# Implementation Plan — сортування замовлень у `GET /api/orders`

Сформовано на основі `inputs/ISSUE_INTAKE.md` та `inputs/INVESTIGATION_NOTE.md`. Це лише план — до коду та тестів зміни не вносяться.

## Goal

Зробити `GET /api/orders` детермінованим: список замовлень користувача повертається строго за спаданням дати створення (нові зверху). При однакових датах створення порядок залишається стабільним — додатковий критерій за спаданням `id` (більший `id` ≈ пізніше створене замовлення → перше). Поведінка покривається автоматичними тестами.

## Scope

- Додати явне сортування в `OrderService.listOrders()` (сервісний шар): за спаданням `createdAt` з tie-breaker за спаданням `id`.
- Визначити та задокументувати обробку `null` у `createdAt` (наприклад, `nullsLast` — записи без дати в кінець списку).
- Покрити поведінку тестами в `OrderServiceTest`: різні дати, рівні дати, порожній список, стабільність повторних викликів.
- Перевірити/актуалізувати `OrderControllerTest`, щоб ендпоінт віддавав відсортований список.
- Закрити відкрите питання з intake: сортування виконується в сервісному шарі, а не на рівні запиту до БД (обґрунтування — нижче).

## Non-goals

- Зміни схеми БД, міграції, додавання індексу на `created_at`.
- Зміна запиту в `OrderRepository.findAllForUser()` — щоб не впливати на інших викликачів, що покладаються на поточний порядок.
- Сортування на рівні БД (`ORDER BY`) — потенційний наступний крок-оптимізація після підтвердження індексу, але не частина цього фіксу.
- Зміна контракту інших ендпоінтів, пагінація, фільтрація.
- Зміна способу встановлення/типу поля `createdAt`.

## Affected files

- `src/main/java/com/rush/orders/OrderService.java` — додати сортування в `listOrders()`.
- `src/main/java/com/rush/orders/OrderController.java` — без змін (передає результат сервісу як є); лише перевірка.
- `src/main/java/com/rush/orders/OrderRepository.java` — без змін (рішення: сортування в сервісі).
- `src/test/java/com/rush/orders/OrderServiceTest.java` — нові тести сортування.
- `src/test/java/com/rush/orders/OrderControllerTest.java` — перевірка/актуалізація тесту ендпоінта.

## Ordered steps

1. Написати фейлінг-тест (TDD): у `OrderServiceTest` створити два замовлення з різницею в кілька секунд і переконатися, що новіше перше. До змін тест падає — відтворення багу.
2. Додати сортування в `OrderService.listOrders()`: `Comparator.comparing(Order::getCreatedAt, reverseOrder()).thenComparing(Order::getId, reverseOrder())` з детермінованою обробкою `null` дати (`nullsLast`).
3. Додати тест на рівні дати: однаковий `createdAt` → більший `id` перший.
4. Додати тест на порожній список: повертається порожній список без помилок.
5. Додати тест на стабільність: повторні виклики `listOrders()` дають однаковий порядок.
6. Перевірити `OrderControllerTest`: `GET /api/orders` повертає відсортований список; оновити фікстури, якщо тест раніше залежав від довільного порядку.
7. Прогнати весь тестовий набір і переконатися, що все зелене.

## Task risk list

- **Інші викликачі `findAllForUser()`**: невідомо, чи хтось покладається на порядок вставки. Сортування в сервісі їх не зачіпає (репозиторій не змінюється), тож ризик низький; перевірку наявності інших викликачів зафіксувати перед релізом.
- **Рівні дати створення**: без tie-breaker порядок недетермінований; знімається порівнянням за `id` за спаданням.
- **`null` у `createdAt`**: компаратор може кинути NPE; обробляється `nullsLast`.
- **Продуктивність**: сортування в пам'яті для списку замовлень користувача — прийнятно; непідтверджений індекс на `created_at` перестає бути блокером, бо запит до БД не змінюється.
- **Тип/часова зона дати**: порівняння коректне, якщо всі елементи списку мають узгоджений тип `createdAt`; перевірити в тестах.
- **Регресія тестів контролера**: якщо тест спирався на невідсортований порядок — оновити фікстури, не послаблюючи перевірок.

## Verification strategy

- Unit-тести `OrderServiceTest` (обов'язково):
  1. різні дати → новіше перше;
  2. рівні дати → більший `id` перший;
  3. порожній список → порожньо, без помилок;
  4. повторні виклики → той самий порядок.
- `OrderControllerTest`: `GET /api/orders` віддає відсортований список (наскрізна перевірка через сервіс).
- Весь тестовий набір проєкту — зелений.
- Smoke-перевірка (якщо середовище доступне): створити два замовлення з різницею в секунди, зробити `GET /api/orders`, переконатися, що нове перше.

## Stop conditions

- Фейлінг-тест із кроку 1 стає зеленим після змін.
- Усі нові тести сортування та весь існуючий набір проходять.
- Приймальні критерії з `ISSUE_INTAKE.md` виконані:
  - `GET /api/orders` повертає замовлення строго за спаданням дати створення;
  - поведінка стабільна при рівних датах і покрита тестом.

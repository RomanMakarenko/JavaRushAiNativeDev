# Implementation Plan — Детерміноване сортування у `GET /api/notifications`

> План складено лише на основі read-only артефактів `inputs/ISSUE_INTAKE.md` та `inputs/INVESTIGATION_NOTE.md`.
> Код проєкту й тести на цьому етапі не змінювалися. Призначений для затвердження людиною.

## Goal

Зробити видачу `GET /api/notifications` детермінованою та передбачуваною:

- сповіщення сортуються **за спаданням дати створення** (найсвіжіші зверху);
- за рівних дат є **стабільний tie-breaker**, тож порядок однаковий між повторними викликами;
- (після продуктового підтвердження) непрочитані сповіщення можуть мати пріоритет вище за дату створення;
- новий порядок **покритий тестом** і не ламає контракт відповіді API.

## Scope

- Додати явне сортування у ланцюжок `NotificationController.list()` → `NotificationService.listForUser()` → `NotificationRepository.findByUser()`.
- Сортування на рівні SQL-запиту репозиторію (переважний варіант) або стабільним компаратором у сервісі — остаточно за результатом перевірки наявних невідомих.
- Вторинний критерій сортування для стабільності за рівних дат (наприклад, `id DESC`).
- Розширення/оновлення тестів модуля сповіщень для фіксації порядку.
- Тільки серверна частина; серіалізована відповідь і шлях ендпоінта не змінюються.

## Non-goals

- Не змінювати формат/контракт відповіді `GET /api/notifications`.
- Не додавати пагінацію, фільтри, пуш-повідомлення чи фонові задачі.
- Не змінювати поведінку інших сценаріїв сповіщень (позначення прочитаним, видалення, створення).
- Не впроваджувати пріоритет unread самостійно — це продуктове рішення, яке вимагає підтвердження людини (див. «Рішення для затвердження»).
- Не міняти фронтенд і не чіпати клієнтський кеш; вплив на них лише оцінюється в ризиках.
- Не виконувати міграції даних.

## Ordered steps

0. **Підтвердження невідомого (read-only).**
   - Перевірити SQL-мапінг `NotificationRepository.findByUser()`: чи вже є `ORDER BY` (тоді сортування могло губитися на іншому рівні).
   - Перевірити наявність і тип поля `createdAt` у сутності `Notification` (містить час чи лише дату; чи є взагалі).
   - Перевірити, чи `listForUser()` застосовує пагінацію або іншу трансформацію, що впливає на порядок.
   - **Очікуваний результат:** зафіксовано, де зараз губиться порядок, і який критерій доступний для сортування.

1. **Вибір рівня сортування.**
   - Пріоритет: сортування на рівні БД (використовує індекс, стабільно за пагінації).
   - Запасний варіант: стабільний `Comparator` у сервісі, якщо сортування в SQL неможливе (наприклад, дані з різних джерел).
   - **Очікуваний результат:** зафіксовано місце зміни в плані реалізації.

2. **Реалізація сортування у `NotificationRepository`.**
   - Оновити запит до `ORDER BY createdAt DESC, id DESC` (або новий метод, якщо існуючий використовується з іншою метою).
   - За погодженням пріоритету unread: `ORDER BY read ASC, createdAt DESC, id DESC`.
   - **Очікуваний результат:** репозиторій повертає сповіщення у фіксованому порядку.

3. **Реалізація в `NotificationService` (лише за варіантом компаратора).**
   - У `listForUser()` застосувати стабільне сортування списку з тим самим компаратором (дата `DESC`, tie-breaker, опційно unread першим).
   - **Очікуваний результат:** сервіс гарантує порядок незалежно від того, що повернула БД.

4. **Тести порядку.**
   - У `NotificationServiceTest` додати кейси: (1) найсвіжіші зверху; (2) рівні дати → порядок визначається tie-breaker; (3) два послідовні виклики дають однаковий порядок; (4) за погодженням — непрочитані вище за прочитані з тією самою датою.
   - За наявності інтеграційного тесту репозиторія — продублювати кейс порядку на рівні запиту.
   - **Очікуваний результат:** порядок зафіксовано тестами.

5. **Перевірка відсутності регресій.**
   - Прогнати повний тест-сюїт модуля сповіщень.
   - Знайти всі інші використання `findByUser()`/`listForUser()` і переконатися, що ніхто не покладається на поточний (випадковий) порядок.
   - **Очікуваний результат:** жодних зламаних сценаріїв.

6. **Мануальна перевірка ендпоінта.**
   - Із фіксованими фікстурами (різні дати, рівні дати, read/unread) викликати `GET /api/notifications`.
   - Переконатися в очікуваному порядку та в тому, що повторні виклики дають той самий результат.
   - **Очікуваний результат:** ендпоінт віддає свіжі сповіщення зверху стабільно.

## Verification strategy

- **Автотести (основне):** кейси порядку з кроку 4 — детермінізм, спадання дати, tie-breaker, опційно unread першим.
- **Повний тест-сюїт модуля сповіщень** — зелені тести без регресій.
- **Мануальна перевірка:** `GET /api/notifications` із фіксованими фікстурами; порядок відповідає очікуваному.
- **Перевірка стабільності:** два послідовні виклики повертають ідентичний порядок.
- **Перевірка контракту:** серіалізований формат відповіді не змінився (порівняти поля до/після).
- **Регресійна перевірка використань:** інші споживачі `findByUser()`/`listForUser()` не залежать від старого порядку.

## Stop conditions

- Усі тести модуля сповіщень зелені.
- Acceptance-критерії з `ISSUE_INTAKE.md` виконані: `GET /api/notifications` сортує за спаданням дати створення; порядок стабільний і покритий тестом.
- Продуктове рішення про пріоритет unread підтверджено (або явно зафіксовано, що пріоритету немає).
- Жодних регресій в інших сценаріях сповіщень та інших споживачах `findByUser()`/`listForUser()`.
- Мануальна перевірка ендпоінта пройдена, формат відповіді не змінився.
- **Scope expansion (стоп із ескалацією):** якщо в процесі реалізації виявляється потреба вийти за початковий обсяг — зокрема відсутність поля `createdAt` у сутності/схемі (що вимагало б міграції даних або зміни сутності) або необхідність нового індексу на `createdAt` для продуктивності — робота **зупиняється** без подальших змін, а рішення про розширення обсягу виноситься на затвердження людиною.

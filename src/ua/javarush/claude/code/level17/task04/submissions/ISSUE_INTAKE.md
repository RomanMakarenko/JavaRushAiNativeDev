# ISSUE INTAKE — Issue #482: оформлення замовлення падає за порожнього кошика

Джерела: `inputs/issue.md`, `inputs/product-comment.md`, `inputs/support-log.md`, `inputs/frontend-note.md`.
Це документ для investigation — код поки не змінюємо.

## Problem

`POST /api/orders` з порожнім `items[]` падає на бекенді з `ArithmeticException: / by zero`
у `OrderService.calculateTotal` (`OrderService.java:88`), викликаному з `OrderController.createOrder`
(`OrderController.java:54`). Замість зрозумілої бізнес-помилки клієнт отримує `HTTP 500`,
користувач бачить загальне повідомлення «щось пішло не так», замовлення не оформлюється.

## User impact

- За останні 7 днів — 12 звернень до підтримки з тим самим сценарієм «порожній кошик → помилка» (`support-log.md`).
- Користувачі бачать загальне повідомлення «щось пішло не так» і не розуміють, що робити; частина йде
  і не повертається до оформлення — втрачена конверсія (`support-log.md`).
- Можливо, сценарій частіше трапляється в мобільному застосунку, але точних метрик немає (`support-log.md`).
- Окрім UX, це реальний збій бекенду (необроблений виняток → `500`), тобто аспект стабільності/доступності сервісу.

## Known evidence

- Stack trace (`issue.md`):
  ```
  java.lang.ArithmeticException: / by zero
      at com.rush.commerce.order.OrderService.calculateTotal(OrderService.java:88)
      at com.rush.commerce.order.OrderController.createOrder(OrderController.java:54)
  ```
- Відтворюється при `POST /api/orders` з порожнім `items[]` (`issue.md`).
- На фронті за статусу `500` показується загальний toast; клієнт не вміє відрізняти порожній кошик
  від інших помилок (`frontend-note.md`).
- Поточний контракт помилки: `{ "error": "...", "code": "..." }` (`frontend-note.md`).
- 12 звернень до підтримки за 7 днів з однаковим сценарієм (`support-log.md`).
- Продукт підтверджує: користувач має розуміти, що кошик порожній, і бекенд не має падати (`product-comment.md`).
- Гіпотеза автора тікета: «напевно, треба додати перевірку в `OrderController`» — це припущення,
  а не підтверджена причина (`issue.md`).

## Requirements

- Бекенд не має падати за порожнього кошика: замість `500` віддавати коректну клієнтську помилку (`4xx`) (`product-comment.md`).
- Користувач має отримати зрозуміле повідомлення, що кошик порожній (`issue.md`, `product-comment.md`).
- Зберегти/узгодити контракт помилки `{ "error": "...", "code": "..." }`; зміна статусу або формату
  потребує оновлення обробки на клієнті (`frontend-note.md`).
- Фронтенд має мати змогу відрізняти «порожній кошик» від інших помилок.
- Попередня пропозиція фронтенду: `400` із полем `code` — потребує узгодження (`frontend-note.md`).

## Assumptions

- `ArithmeticException: / by zero` у `calculateTotal` найімовірніше виникає через ділення на розмір
  колекції `items` (наприклад, розрахунок середнього/пропорції) — це потребує підтвердження по коду `OrderService:88`.
- Рут-причина — у логіці `OrderService.calculateTotal`; контролер не має захисної перевірки порожнього `items[]`.
- Порожній кошик — легітимний стан, досяжний користувачем (наприклад, елемент прибрано перед оформленням).
- Цільовий фікс локалізується в межах flow оформлення замовлення; інші flow не зачіпаємо.
- Зміна статусу відповіді на `400` (і/або нового `code`) вимагає координації з фронтендом.

## Open questions

- Яка точна причина `ArithmeticException` на `OrderService.java:88` — ділення саме на `items.size()`?
  Який код навколо рядка 88?
- Де розміщувати валідацію: у `OrderController` (гіпотеза з тікета) чи в `OrderService`?
- Який саме HTTP-статус і `code` повертати: `400` + якийсь код на кшталт `EMPTY_CART`? Чи узгоджений він із фронтендом?
- Чи додавати код `EMPTY_CART` для аналітики зараз — продукт каже «пізніше», потрібне фінальне підтвердження для цього тікета.
- Чи справді мобільний застосунок зачеплено частіше, і чи потрібно збирати метрики для пріоритизації?
- Чи є інші місця виклику `calculateTotal`/`createOrder`, які зачіпить зміна поведінки?
- Чи потрібні тести (unit/інтеграційні) на сценарій порожнього кошика?

## Out of scope

- Редизайн кошика та будь-які зміни flow для непорожнього кошика (`product-comment.md`).
- Окремий код `EMPTY_CART` для аналітики — відкладено на пізніший тікет (`product-comment.md`).
- Зміни в логіці оформлення для валідних замовлень.

## Risk notes

- **Координація з фронтендом:** зміна статусу (`500` → `400`) або формату відповіді без оновлення клієнта
  зламає обробку помилок на фронті (`frontend-note.md`).
- **Неповний фікс:** якщо захист додати лише в контролер, інші викликачі `OrderService.calculateTotal`
  можуть продовжити падати — корінь проблеми в сервісі.
- **Регресія:** без тестового покриття сценарій «порожній кошик» може знову відкотитися до `500`.
- **Відсутність метрик:** через нерозуміння частки мобільного застосунку реальний вплив може бути недооцінений.
- **Відкладена аналітика:** без `EMPTY_CART`-коду цей сценарій залишиться невидимим в аналітиці до наступного тікета.

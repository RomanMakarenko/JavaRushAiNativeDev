# Сценарії для класифікації перевірок

Проєкт: e-commerce платформа `acme/commerce`.
Нижче три ситуації. Для кожної потрібно вирішити, який рівень перевірки мінімально
достатній: `Smoke`, `Regression` або `E2E`.

## Сценарій 1 — баг після retry

У promo engine виявлено відтворюваний дефект: повторний виклик `applyPromotion`
для однієї й тієї самої корзини дублює знижку (double discount). Баг локалізовано в
одному методі, корінь зрозумілий, фікс буде вузьким.

- Ризик: повтор регресії в майбутньому (легко випадково повернути багом у тій самій логіці).
- Масштаб: один метод, чиста бізнес-логіка, без UI та мережі.

## Сценарій 2 — критичний шлях checkout

Перед кожним PR у main команда хоче швидкий сигнал, що головний грошовий шлях
(оформлення замовлення, checkout) узагалі живий. Повний сценарій "поклав у корзину →
оплатив → отримав підтвердження" критичний для бізнесу.

- Ризик: тихе ламання критичного шляху = прямі втрати виручки.
- Масштаб: наскрізний шлях через кілька шарів і зовнішніх залежностей.

## Сценарій 3 — сортування таблиці в адмінці

В адмін-панелі поправили порядок сортування колонки "дата" в таблиці замовлень.
Це рідко використовуваний внутрішній екран, ціна помилки низька, відновлення
тривіальне.

- Ризик: косметичний, низька бізнес-критичність.
- Масштаб: один UI-віджет у внутрішньому інструменті.

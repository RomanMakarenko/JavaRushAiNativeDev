# WIDE — класифікація перевірок

Проєкт: e-commerce платформа `acme/commerce`.
Документ класифікує всі три сценарії з `inputs/scenarios.md` на рівні
`Smoke`, `Regression` або `E2E`. Вибір керується принципом **мінімально
достатнього рівня** з урахуванням вартості підтримки тесту та типу ризику.

## Критерії (з `inputs/CLAUDE.md`)

| Рівень | Призначення | Коли брати |
| --- | --- | --- |
| `Smoke` | швидкий вузький сигнал «критичний шлях живий», дешевий, запускається часто | потрібен частий зворотний сигнал живучості |
| `Regression` | один захисний сценарій на один уже відтворений баг / конкретну поведінку | вже відомо, що саме може зламатися, і де |
| `E2E` | дорогий наскрізний сценарій через UI та зовнішні залежності | тільки справді критичні шляхи, коли нижчий рівень не дає сигналу |

---

## Сценарій 1 — баг після retry (double discount)

**Категорія: `Regression`** — не E2E.

Чому саме цей вибір мінімально достатній:

- **Тип ризику.** Баг уже відтворено й корінь зрозумілий; головна загроза — не поточне
  ламання, а *повтор* регресії в тій самій логіці. Це дослівно випадок під `Regression`
  за визначенням: один захисний тест на один відомий дефект. Unit-тест, що двічі викликає
  `applyPromotion` на одній корзині й перевіряє, що знижка не подвоїлась, жорстко фіксує
  виправлення.
- **Масштаб.** Один метод, чиста бізнес-логіка без UI та мережі — тест на рівні методу
  повністю покриває дефект. Підніматися вище по стеку нема чого.
- **Вартість підтримки.** Мінімальна: швидкий, детермінований, стабільний тест без
  зовнішніх залежностей; прив'язаний до одного методу, тому дешевий у підтримці.
- **Не робимо E2E.** Наскрізний сценарій через UI і мережу не дасть жодного додаткового
  сигналу про double discount (логіка в одному методі), натомість додасть повільність,
  нестабільність і постійну вартість супроводу. Ризик, який закривається, цілком
  покривається дешевим unit-тестом.

## Сценарій 2 — критичний шлях checkout

**Категорія: `Smoke`** — не E2E (як гейт перед кожним PR).

Чому саме цей вибір мінімально достатній:

- **Тип ризику.** Тихе ламання грошового шляху = прямі втрати виручки, тому сигнал
  потрібен *частий* — перед кожним PR у main. Це і є призначення `Smoke`: дешевий,
  вузький сигнал «шлях узагалі живий», який можна ганяти часто.
- **Масштаб.** Шлях іде через кілька шарів, але Smoke проходить щасливий шлях
  (корзина → оплата → підтвердження) наскрізь достатньо, щоб упіймати ламання
  інтеграції між шарами, залишаючись швидким і стабільним.
- **Вартість підтримки.** Порівняно з E2E — значно нижча: Smoke залежить від меншого
  числа рухомих частин, рідше ламається через флейкі та простіше оновлюється.
- **Не робимо повноцінний E2E.** Наскрізний E2E через справжні зовнішні залежності
  (платіжний провайдер) перед кожним PR буде повільним і нестабільним, а його підтримку
  доведеться оплачувати постійно — при тому, що для сигналу «шлях живий» він не додає
  нової інформації. Набір нестабільних E2E гірший за кілька надійних (принцип з
  `inputs/CLAUDE.md`). Якщо колись знадобиться валідація повної реальної транзакції зі
  зовнішньою системою, це окремий запланований E2E поза PR-гейтом — а не частина
  частого сигналу.

## Сценарій 3 — сортування таблиці в адмінці

**Категорія: `Regression`** — не E2E.

Чому саме цей вибір мінімально достатній:

- **Тип ризику.** Косметичний, низька бізнес-критичність, відновлення тривіальне.
  Потрібен не глибокий захист, а лише закріплення конкретної зміненої поведінки —
  нового порядку сортування колонки «дата». Це вузький захисний сценарій на
  відому зміну: `Regression`.
- **Масштаб.** Один UI-віджет у внутрішньому інструменті — достатньо одного
  фокусного тесту на віджет, який падає, якщо сортування знову «перевернуть».
- **Вартість підтримки.** Один тест на один віджет, пропорційний ціні помилки;
  дешево оновлювати, дешево ігнорувати як непріоритетний при зміні екрана.
- **Не робимо E2E.** Внутрішній рідко використовуваний екран із низькою ціною
  помилки не виправдовує наскрізного сценарію через весь стек і зовнішні залежності —
  це було б непропорційно дорого й нестабільно заради косметичного ризику.
  **Не `Smoke`:** цей екран не критичний шлях, і використовувати Smoke тут розмивало б
  його призначення («критичний шлях живий»), даючи частіший сигнал, ніж потрібно
  для такої низької критичності.

## Підсумок

| Сценарій | Категорія | Ризик | Чому не E2E |
| --- | --- | --- | --- |
| 1. Double discount | `Regression` | повтор відомого бага | чиста логіка без UI/мережі — unit-тест покриває повністю |
| 2. Checkout | `Smoke` | тихе ламання = втрата виручки | перед кожним PR потрібен швидкий сигнал; E2E повільний і нестабільний |
| 3. Сортування в адмінці | `Regression` | косметичний, низька критичність | один віджет, відновлення тривіальне — E2E непропорційний |

Усі три сценарії закриті без повноцінного E2E: у кожному випадку сигнал,
що його потрібно отримувати, дається дешевшим і стабільнішим рівнем, а вартість
підтримки наскрізного сценарію не окупається типом ризику.

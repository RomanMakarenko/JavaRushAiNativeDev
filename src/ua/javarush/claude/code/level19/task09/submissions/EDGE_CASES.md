# EDGE_CASES — крайові випадки для `POST /api/orders/{id}/refund`

Design-матеріал для тестування refund flow. Аналіз обмежений `RefundController` / `RefundService`; тести не пишуться, production-файли не змінюються.

Контекст: тіло запиту — `amount` (long) та `reason` (String); право на повернення — роль `REFUND_MANAGER`; вікно повернення — 30 днів, межа рахується в UTC.

## invalid input
`amount ≤ 0` (або відсутній/порожній `reason`, або невалідний `id` у шляху) проходить без валідації → замість `400 Bad Request` сервіс повертає `500` або виконує некоректне повернення.

## boundary
Повернення рівно на 30-й день після замовлення — потрібно зафіксувати, чи межа inclusive чи exclusive; окремо: `amount` на межі допустимого діапазону та ризик переповнення `long`.

## permissions
Запит від користувача без ролі `REFUND_MANAGER` (або роль перевірена до початку операції, але знята в момент виконання — TOCTOU) приводить або до несанкціонованого повернення, або до відмови легітимному менеджеру.

## duplicate request
Той самий refund-запит (той самий `orderId` + `amount` + `reason`) надходить двічі — через ретрай клієнта, подвійне натискання або повторне надсилання, і за відсутності ідемпотентності кошти повертаються двічі.

## timeout
Зовнішній виклик (напр., платіжний gateway) не встигає в ліміт часу — клієнт отримує таймаут, повторює запит, а операція насправді вже виконана, що лишає стан замовлення невизначеним.

## timezone
Замовлення, зроблене за кілька хвилин до півночі UTC, перетинає 30-денну межу в часовому поясі клієнта — повернення помилково приймається або відхиляється через різницю в часових поясах та DST.

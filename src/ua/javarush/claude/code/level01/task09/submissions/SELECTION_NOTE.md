# Аналіз методу `calculateRefund`

**Файл:** `src/main/java/com/example/refunds/RefundService.java` (рядки 21–28)

---

## Що робить метод

Метод обчислює суму грошей, яку потрібно повернути клієнту:

1. Бере повну суму замовлення (`orderAmount`) та віднімає знижку (`discount`).
2. Якщо отримана сума перевищує ліміт `MAX_REFUND` (10 000.00), обрізає її до цього ліміту.
3. Повертає результат, округлений до двох знаків після коми за правилом `HALF_UP`.

**Логіка автора:** «клієнт має отримати назад те, що реально заплатив» — тобто сума замовлення мінус знижка.

---

## Ризики

| Ризик | Наслідок |
|---|---|
| **`discount` може бути `null`** | `BigDecimal.subtract(null)` викине `NullPointerException` у рядку 23 — метод не має жодної перевірки на `null`. |
| **`orderAmount` може бути `null`** | Аналогічний `NullPointerException` при виклику `subtract`. |
| **`discount` більший за `orderAmount`** | Результат буде **від'ємним** (наприклад, 50.00 − 100.00 = −50.00). Повернення від'ємної суми — семантична помилка; клієнт має отримати 0.00 або метод має кидати виняток. |
| **Немає валідації вхідних параметрів** | Жодна з негативних ситуацій вище не обробляється — метод покладається на те, що викликаючий код передав коректні дані. |
| **`MAX_REFUND` — це ліміт суми повернення, а не суми замовлення** | Якщо замовлення було на 15 000.00 зі знижкою 2 000.00, клієнт заплатив 13 000.00, але отримає лише 10 000.00. Чи це бажана поведінка — залежить від бізнес-логіки, але в методі немає коментаря, чому ліміт застосовується саме так. |
| **Округлення завжди `HALF_UP`** | Якщо бізнес-вимоги зміняться (наприклад, `HALF_DOWN` або `HALF_EVEN` для фінансової звітності), метод доведеться змінювати — воно «зашите» всередині, а не параметризоване. |

## Граничний випадок (edge case)

**`orderAmount` менший за `MAX_REFUND`, `discount` дорівнює 0.00:**

```
calculateRefund(new BigDecimal("9999.99"), BigDecimal.ZERO) → 9999.99
```

Тут усе коректно. Але варто розглянути цікавіший сценарій:

```
calculateRefund(new BigDecimal("0.00"), new BigDecimal("0.00")) → 0.00
```

Сума замовлення 0.00 — це валідний `BigDecimal`, метод не зламається, але чи має сенс бізнес-кейс «повне замовлення на 0.00»? Якщо ні — варто додати валідацію на `orderAmount.compareTo(BigDecimal.ZERO) <= 0`.

Найнебезпечніший граничний випадок — **обидва параметри `null`**: метод упаде з `NullPointerException`, не дійшовши до жодної логіки.

# PR DRAFT — issue-432: порожній кошик має повертати 400 замість 500

## What changed
- `OrderController` (новий): ендпоінт `POST /api/orders`. Додано ранню валідацію кошика — якщо `items` дорівнює `null` або порожній, метод одразу повертає `400 Bad Request` із тілом `Cart is empty`, не доходячи до обчислення суми. Для непорожнього кошика повертається `200` із тілом `Order accepted`.
- `OrderRequest` та `OrderItem` (нові records): модель тіла запиту — список позицій, кожна позиція має поля `sku` та `quantity`.
- `docs/ISSUE.md` (новий): опис issue-432 з поточною та очікуваною поведінкою.
- `inputs/test-output.txt` (новий): свідчення успішного запуску тесту `OrderControllerTest.returnsBadRequestForEmptyCart`.

## Why
Запит `POST /api/orders` із порожнім списком позицій (`items: []`) раніше завершувався `500 Internal Server Error` — падіння ставалося під час спроби обчислити суму замовлення за порожнім списком. Порожній кошик — це помилка клієнта, тому ендпоінт має відповідати `400 Bad Request` із зрозумілим тілом `Cart is empty`, і валідація має спрацьовувати до будь-яких обчислень суми.

## How to test
1. Запустити тест (команда з `inputs/test-output.txt`):
   `./gradlew :orders:test --tests OrderControllerTest.returnsBadRequestForEmptyCart`
   Очікується `BUILD SUCCESSFUL`, тест `returnsBadRequestForEmptyCart() PASSED`.
2. Перевірити ендпоінт вручну:
   - `POST /api/orders` із тілом `{"items": []}` → очікується статус `400` і тіло відповіді `Cart is empty`.
   - `POST /api/orders` із тілом `{"items": [{"sku": "A-1", "quantity": 2}]}` → очікується статус `200` і тіло відповіді `Order accepted`.

## Risks / edge cases
- Тіло `{}` або `{"items": null}` трактується як порожній кошик (перевірка `items == null`) і також повертає `400` — валідація покриває і `null`, і порожній список.
- Для непорожнього кошика сума не обчислюється і замовлення не зберігається — наразі повертається заглушка `Order accepted`. Це свідоме обмеження цього зрізу, а не повний flow оформлення замовлення.
- Валідація `quantity <= 0` відсутня (див. Out of scope).
- Тіло відповіді — звичайний рядок, а не JSON; контракт відповіді для непорожнього кошика не змінювався.

## Out of scope
- Валідація невалідної кількості позицій (`quantity <= 0`) — обробляється окремим issue згідно з `docs/ISSUE.md`.
- Зміни схеми API та контрактів відповіді для непорожнього кошика (повноцінне обчислення суми, збереження замовлення) — не плануються.
- Обробка інших валідаційних помилок, наприклад відсутність `sku` у позиції.

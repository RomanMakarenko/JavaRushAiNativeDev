# MCP Decision Record — Commerce OS

> **Дата:** 2026-07-17
> **Контекст:** Команда Commerce OS зберігає робочі активи в Workflow Kit.
> **Сесія:** Виконано `/clear` (очищення контексту) та `/context` (верифікація прогріву).
> **Методологія:** Кожен випадок оцінено за трьома вимірами (Value, Frequency, Controllability),
> після чого зроблено підсумковий вибір: `manual | read-only MCP | write-capable MCP`.

---

## Value (Цінність)

| Рівень | Визначення |
|--------|------------|
 | Low | MCP не дає суттєвого приросту — дані вже поруч або дія надто проста |
 | Medium | MCP скорочує ручну роботу, але не змінює принципово процес |
 | High | MCP автоматизує те, що інакше потребувало б перемикання контексту або не відбувалося б узагалі |

## Frequency (Частота)

| Рівень | Визначення |
|--------|------------|
 | Low | Разово або раз на декілька днів |
 | Medium | Декілька разів на день — раз на день |
 | High | Багато разів на день (постійний потік) |

## Controllability (Контрольованість)

| Рівень | Визначення |
|--------|------------|
 | High | Дані/система під повним контролем розробника, без зовнішніх залежностей |
 | Medium | Є зовнішній сервіс, але дія read-only і передбачувана |
 | Low | Зовнішній сервіс, write-дія з реальними побічними ефектами |

---

## Випадок A — одноразовий локальний stack trace

**Опис:** Після невдалого тесту є стек помилки з локального запуску. Проєкт відкрито
поруч, лог перед очима. Потрібно один раз розібрати причину падіння.

| Вимір | Оцінка | Обґрунтування |
|-------|--------|----------------|
| **Value** | `Low` | Данні вже на екрані. MCP-запит до зовнішнього інструмента не пришвидшить аналіз — уся інформація локальна. |
| **Frequency** | `Low` | Один раз (adhoc після падіння тесту). Немає регулярного патерну. |
| **Controllability** | `High` | Стек помилки та проєкт повністю під контролем розробника. Немає зовнішньої системи, до якої треба звертатися. |

**Decision: `manual`**

MCP не виправданий. Вартість налаштування MCP-сервера не окупиться за одну дію.
Розробник швидше скопіює стек вручну, ніж проєктуватиме інтеграцію.

---

## Випадок B — щоденний intake завдань із issue tracker

**Опис:** Щодня в трекері з'являються нові issue Commerce OS (наприклад, COM-481).
Розробник копіює заголовок, опис, мітки та коментарі й просить Claude зібрати
чернетку `TASK_SPEC.md`. Це відбувається багато разів на день.

| Вимір | Оцінка | Обґрунтування |
|-------|--------|----------------|
| **Value** | `Medium` | Автоматизація забирає ручне копіювання полів, але не змінює саму логіку роботи — Claude однаково потрібно проаналізувати контент. |
| **Frequency** | `High` | Багато разів на день. Кожен новий issue — це потенційний MCP-запит. |
| **Controllability** | `Medium` | Issue tracker — зовнішній сервіс, але дія лише читає дані. Немає ризику мутації стану. |

**Decision: `read-only MCP`**

Висока частота окупає налаштування read-only MCP для трекера. Розробник
отримує чистий JSON issue прямо в контекст Claude без ручного копіювання.
Дія лише читає — жодного ризику випадково змінити статус або дані в трекері.

---

## Випадок C — автоматично закривати issue після merge

**Опис:** Ідея: коли PR змёржено, автоматично переводити пов'язаний issue в
статус `Done` через той самий issue tracker. Це write-дія, що змінює зовнішній стан.

| Вимір | Оцінка | Обґрунтування |
|-------|--------|----------------|
| **Value** | `High` | Усуває ручну операцію, яку легко забути. Відповідність між merge та закриттям issue не потребує уваги розробника. |
| **Frequency** | `Medium` | Кожен змержений PR — залежно від темпу команди, від декількох разів на день до декількох на тиждень. |
| **Controllability** | `Low` | Зовнішній сервіс, write-дія з реальними побічними ефектами (issue змінює статус назовні) + зовнішній тригер (PR merge). |

**Decision: `write-capable MCP`**

MCP виправданий, і він має бути write-capable, бо:

1. **Автоматизація pipeline** — це не просто зручність, а усунення manually
   missed step. Без автоматизації частина issue залишатиметься відкритою після merge.
2. **Дія потребує write** — закриття issue не "читання"; помилка випадкового
   закриття має наслідки для інших членів команди (втрата контексту, follow-up),
   тому MCP має бути write-capable з явним дозволом, а не read-only.
3. **За умовою** — рішення не може бути `read-only MCP`, а `manual` не відповідає
   цілі автоматизації.

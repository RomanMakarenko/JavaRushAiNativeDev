# Rollback outline

> **Режим:** read-only pilot. Цей документ описує план і критерії, але не виконує rollback.
> **Обмеження:** змінюється лише цей файл у `submissions/`; файли поза `submissions/` не змінюються.

## CLI preflight

Перед основним запитом усередині Claude CLI були виконані спроби команд перегляду стану та дозволів:

- `/help` — у цій версії Claude CLI команда недоступна.
- `/status` — у цій версії Claude CLI команда недоступна.
- `/permissions` — у цій версії Claude CLI команда недоступна.

CLI також повідомив про невідомий внутрішній ідентифікатор моделі `claude-course-fast`; це не змінює зміст цього read-only документа.

## Code

- **Ціль:** повернутися до останньої підтвердженої стабільної ревізії `[target commit/tag/build]`.
- Зафіксувати поточну ревізію `[current revision]` і створити точку повернення.
- Перевірити diff між поточною та цільовою ревізіями, особливо API, форматами даних і міграціями.
- Підготувати цільовий immutable artifact і виконати smoke/regression-перевірки після перемикання.
- **Критерій успіху:** smoke-перевірки проходять, а ключові помилки інциденту не відтворюються протягом `[observation window]`.

## Dependency

- **Ціль:** відновити dependency manifest і lock-файл, сумісні з `[target revision]`.
- Порівняти поточні та цільові версії прямих і транзитивних залежностей.
- Перевірити checksum/signature артефактів і відтворюваність чистої збірки.
- **Критерій успіху:** чиста збірка та тести сумісності проходять без непогоджених downgrade.

## Config

- **Ціль:** повернути сумісну конфігурацію без розкриття секретів.
- Зберегти snapshot ефективної конфігурації без secret values.
- Перевірити змінні середовища, feature flags, маршрутизацію, resource limits, telemetry та доступність секретів.
- Перевірити конфігурацію в staging перед production.
- **Критерій успіху:** startup, health і readiness checks проходять; секрети не потрапляють у логи або коміти.

## Data

none, because this is a read-only pilot: жодні дані, схеми, міграції, backup-и або записи не змінюються і не відновлюються.

## Deployment

- **Ціль:** підготувати безпечне повернення до `[artifact ID/digest]`; фактичний deployment у межах цього pilot не виконується.
- Зафіксувати поточний deployment, health metrics, трафік і активні jobs/queues.
- Підготувати canary-послідовність: частина інстансів → health checks → повний rollout.
- Контролювати error rate, latency, saturation, queues і бізнесові метрики протягом `[observation window]`.
- **Критерій успіху:** план має однозначні кроки, target artifact і спосіб повернення до поточного стану.

## Abort conditions

Rollback потрібно негайно зупинити, якщо виконується хоча б одна умова:

1. **Помилки:** error rate після canary перевищує baseline більш ніж на **2 процентні пункти** протягом **5 хвилин**.
2. **Доступність:** будь-який обов’язковий health/readiness check має менше **99% успішних відповідей** у вікні **5 хвилин**.
3. **Затримка:** p95 latency перевищує baseline більш ніж на **30%** протягом **10 хвилин**.
4. **Дані:** виявлено будь-яку розбіжність контрольної кількості записів або checksum (**>0** невідповідностей).
5. **Артефакт:** target artifact, checksum або lock-файл не збігається з погодженим значенням (**1 або більше** невідповідностей).

## Після rollback

- Зафіксувати фактичні revision, dependency set, config revision і deployment artifact.
- Перевірити smoke/regression, health/readiness checks і бізнесові метрики.
- Зберегти логи, metrics snapshot, deployment history та incident log.
- Заборонити повторний rollout проблемного artifact до завершення root-cause analysis і forward fix.

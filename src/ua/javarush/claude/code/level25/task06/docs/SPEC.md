# Problem statement

Сервіс показує користувачеві історію підписок, у якій змішані записи зі статусами `active` і `cancelled`. Через це на екрані «Мої підписки» незрозуміло, які підписки діють зараз і за що користувач реально платить. Потрібно відокремити чинні підписки від скасованих у сценарії отримання активного списку.

# Target user

- **Основний користувач:** підписник сервісу, у якого накопичується історія продовжених і скасованих підписок.
- **Потреба:** швидко бачити короткий і достовірний список того, що діє в цей момент.
- **Другорядні читачі специфікації:** ментор і reviewer, які перевіряють відповідність реалізації заявленому контракту.

# Current state

- Це навчальний capstone backend-проєкт на Java та Gradle.
- `GET /subscriptions/active` уже оголошений у контролері.
- У `SubscriptionService` є метод отримання активних підписок, але фактично він повертає всі записи, зокрема `cancelled`.
- Є чорновий тест, який не виявляє цю помилку; regression-тест на правило «тільки активні» відсутній.
- На старті дозволене in-memory сховище; справжня база даних не потрібна.
- Збірка проєкту має виконуватися через `./gradlew build`.

# Desired state

Сценарій `GET /subscriptions/active` повертає JSON-список лише тих підписок користувача, які мають статус `active`. Записи зі статусом `cancelled` не повинні потрапляти у відповідь. Service-логіка, endpoint-контракт і regression-тести мають узгоджено гарантувати це правило, щоб користувач бачив лише чинні підписки.

# Scope

- Реалізувати або виправити фільтрацію підписок за статусом `active` у `SubscriptionService`.
- Зберегти HTTP-контракт `GET /subscriptions/active`.
- Забезпечити повернення результату у форматі JSON-списку.
- Додати regression-тест із набором, де одночасно є `active` і `cancelled`, та перевірити, що у результаті залишаються тільки `active`.
- Використовувати in-memory дані на початковому етапі.

# Non-goals

- Платежі та білінг.
- PDF-експорт списку.
- Сповіщення користувачів.
- Впровадження справжньої бази даних або повноцінної persistence-моделі на цьому етапі.
- Нові endpoint-и та функції, не пов’язані з отриманням активного списку.

# Constraints

- Стек: Java + Gradle.
- Endpoint має мати точний метод і шлях: `GET /subscriptions/active`.
- Відповідь endpoint-а — JSON зі списком підписок.
- На старті можна використовувати in-memory сховище без зовнішньої БД.
- Проєкт виконується одним автором протягом кількох тижнів із рев’ю ментора раз на тиждень.
- Специфікація не фіксує непідтверджених деталей: схему полів, автентифікацію, user context, HTTP-коди помилок і конкретний web/test framework потрібно визначити окремо.

# Acceptance criteria

1. Для набору даних зі змішаними статусами endpoint повертає активні записи, а жоден запис зі статусом `cancelled` не потрапляє до відповіді.
2. `GET /subscriptions/active` існує та повертає JSON-список, сумісний із моделлю підписки.
3. У сервісному шарі є regression-тест, який явно перевіряє правило «повертаються тільки `active`» і не проходить для поточної помилкової реалізації.
4. Для відсутності активних записів повертається порожній список, без включення скасованих записів.
5. Команди `./gradlew test` і `./gradlew build` завершуються успішно.

# Verification plan

1. Запустити `./gradlew test` і переконатися, що regression-тест охоплює змішаний набір `active`/`cancelled`.
2. Запустити `./gradlew build` як перевірку повної збірки.
3. Виконати endpoint-перевірку на in-memory наборі з активними та скасованими записами: перевірити HTTP-виклик `GET /subscriptions/active`, JSON-формат, наявність усіх `active` і відсутність усіх `cancelled`.
4. Окремо перевірити порожній результат, коли активних підписок немає.
5. Передати специфікацію та результати перевірок на планове рев’ю ментора.

# Risks and open questions

- Не визначені точна схема JSON і поля моделі підписки.
- Не визначено, як endpoint ідентифікує користувача та який user context використовує.
- Потрібно уточнити допустимі значення й регістр статусів (`active`/`cancelled`), а також точний enum або рядкове представлення.
- Не визначені сортування, обробка дублікатів, pagination і повна поведінка для порожнього списку на рівні HTTP-контракту.
- Не визначені HTTP-коди та формат помилок для невалідного або відсутнього user context.
- In-memory сховище втрачає дані після перезапуску та не вирішує питання довготривалої persistence і multi-user ізоляції; перехід на БД може потребувати окремого етапу.
- Потрібно підтвердити, що endpoint не лише оголошений, а й фактично коректно серіалізує відповідь; у поточних матеріалах це не уточнено.
- Потрібно уточнити конкретний web- і test framework, якщо це впливає на інтеграційний тест.

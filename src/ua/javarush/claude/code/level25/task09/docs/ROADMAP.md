# Roadmap — MealPlan

Стислий milestone-план для першої версії capstone-проєкту. План спирається на контракт у [`SPEC.md`](SPEC.md) і підтримує один відтворюваний core flow: користувач обирає день, додає страву та бачить оновлений список.

## Milestones

| Віха | Результат | Критерій готовності | Evidence |
|---|---|---|---|
| M0 — Контракт і каркас | Зафіксовано scope, non-goals і структуру застосунку | Реалізація не виходить за межі одного core flow; документація узгоджена | Запис рішення/зміни в evidence log |
| M1 — Вибір дня | Користувач може обрати день тижня | Обраний день однозначно відображений і використовується наступною дією | Локальний smoke-крок з обраним днем |
| M2 — Додавання страви | Страва додається до плану обраного дня | Після додавання дані прив’язані саме до вибраного дня; порожній/некоректний ввід не створює хибного запису | Smoke-крок додавання + evidence log |
| M3 — Оновлений список | Користувач бачить актуальний список страв цього дня | Новий запис відображається без неоднозначності; перемикання дня показує відповідний список | Smoke-перевірка повного core flow |
| M4 — Перевірка й traceability | Core flow відтворюється локально, документація актуальна | Smoke-перевірка проходить стабільно; кожен значущий крок має evidence; roadmap і SPEC не суперечать одне одному | Команда перевірки та фінальний evidence log |

## Порядок виконання

1. Спочатку закріпити M0, щоб не розширювати scope під час реалізації.
2. Реалізувати M1 → M2 → M3 як послідовні вертикальні slices.
3. Після кожної ві́хи запускати найменшу доступну локальну перевірку й додавати evidence.
4. Завершити M4 лише після повторного проходження всього сценарію від вибору дня до оновленого списку.

## Escalation policy для зірваних віх

Віха вважається зірваною, якщо її критерій готовності не виконано у запланованому slice або перевірка дає нестабільний результат.

- **Рівень 1 — відхилення:** зафіксувати факт у evidence log, назвати блокер і не переходити до залежних віх.
- **Рівень 2 — triage:** перевірити останню зміну, відтворити проблему локально та звузити її до сценарію, даних або документації. Нові функції й non-goals на цьому етапі не додаються.
- **Рівень 3 — корекція:** розбити ві́ху на менший slice, виправити мінімальну причину та повторити smoke-перевірку. Якщо причина в scope, повернутися до SPEC, а не розширювати його мовчки.
- **Рівень 4 — перегляд траєкторії:** якщо дві послідовні спроби не відновили критерій або блокер зачіпає core flow, зупинити подальше нарощування, оновити roadmap/evidence і переглянути порядок milestones.
- **Правило прозорості:** жодна віха не позначається як готова без відтворюваного evidence; пропущені перевірки явно позначаються як `blocked` або `not verified`.

## Grading preview

Стислий preview критеріїв оцінювання:

- **Core flow:** користувач обирає день, додає страву, бачить оновлений список саме цього дня.
- **Коректність scope:** реалізовано один заявлений flow; рецепти, калорії, акаунти та синхронізація не підміняють acceptance criteria.
- **Перевірюваність:** локальна smoke-перевірка відтворювана й охоплює весь сценарій.
- **Evidence:** кожен значущий крок має короткий traceable запис.
- **Документація:** SPEC, README і ROADMAP узгоджені та не містять непідтверджених claims.

## Defense 4 pillars

1. **Problem** — тримати фокус на проблемі: зібрати тижневий план харчування в одному місці, не розширюючи задачу до рецептів, калорій чи акаунтів.
2. **Core scenario** — захистити наскрізний flow: користувач обирає день, додає страву до цього дня та бачить оновлений список.
3. **Workflow + verification** — виконувати роботу короткими slice-ами, після кожної ві́хи запускати локальну smoke-перевірку й фіксувати значущі кроки в evidence log.
4. **Limitations & trade-offs** — явно приймати обмеження першої версії: без рецептів, калорій, синхронізації між пристроями та акаунтів; натомість зберігати простий, відтворюваний core flow.

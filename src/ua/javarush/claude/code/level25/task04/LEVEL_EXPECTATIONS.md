# Очікування за рівнями для capstone

Документ описує, чого очікують від capstone-проєкту на кожному рівні. Обирається рівно
один рівень. Рівень визначає глибину інженерної роботи, а не кількість фіч.

## Junior

- Реалізовано один core flow від початку до кінця.
- Є робочий локальний запуск за README без прихованих кроків.
- Присутній базовий набір тестів на головний сценарій.
- Документація пояснює, що робить проєкт і як його запустити.
- Допустимий demo-ready результат без production-інфраструктури.

## Middle

- Реалізовано один core flow з обробкою основних помилок.
- Є SPEC.md з goal, scope і non-goals.
- Тести покривають happy path і щонайменше один negative scenario.
- Видно контрольований workflow: план, невеликі diff, evidence log.
- Є базова verification (тести або smoke-команда), що запускається локально.
- Допустимий demo-ready результат, production deploy не обов'язковий.

## Senior

- Core flow виділено в чисту межу з явним контрактом модуля.
- SPEC.md доповнено acceptance criteria і verification plan.
- Тести включають unit, negative і regression на ключовий інваріант.
- Видно усвідомлений вибір архітектурних меж і обґрунтування trade-offs.
- Verification harness автоматизований і відтворюваний.
- Demo-ready результат з явним розділенням demo-режиму та production-намірів.

## Anti-scope guardrails

- Production deployment не входить до обов'язкового scope ні на одному рівні.
- Multi-agent orchestration не потрібна для проходження capstone.
- Зовнішні інтеграції (платежі, Figma, MCP) не повинні бути обов'язковими.
- Роздування scope кількома незалежними flow вважається помилкою, а не плюсом.

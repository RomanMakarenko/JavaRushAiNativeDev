# Рішення щодо ізоляції: субагент tester для refund flow

**Issue:** після partial refund eligibility вважається неправильно, regression test цього не ловить.
Робота ділиться на дві фази — у кожної своя ізоляція і своя проблема.

## Дві фази — дві різні ізоляції

| Фаза | Що робить tester | Головна проблема без ізоляції | Рішення |
|------|------------------|-------------------------------|---------|
| 1. Дослідження | Читає код тестів, шукає refund логіку, збирає evidence | Зайвий шум в індексації, випадкова зміна файлу під час огляду | Context isolation — read-only інструменти (немає Edit/Write) |
| 2. Правки | Виправляє eligibility calculation і тести | Частковий коміт, зламаний main, Regression test падає під час роботи | Worktree isolation — окрема директорія й гілка субагента |

## Матриця вибору: що захищаємо, яка проблема, що вибираємо

| Критерій | Фаза 1: Дослідження | Фаза 2: Правки |
|----------|---------------------|-----------------|
| **Що захищаємо** | Чистоту поточного стану — tester не повинен випадково змінити код під час розвідки | Стабільність main-гілки та контекст основної сесії |
| **Проблема без ізоляції** | Агент із повним набором інструментів може випадково зберегти зміни під час дослідження, «засмітити» робочу директорію або індексацію IDE | Правки в основній сесії змішуються з іншими завданнями; незавершені зміни ламають тести на main; коміт може бути частковим |
| **Що вибираємо** | Context isolation — обмеження інструментів на рівні дескрипції агента (Read / Grep / Bash, без Edit і Write) | Worktree isolation — `git worktree add` в `.claude/worktrees/tester-refund` на окремій гілці `agent/tester-refund` |
| **Чому підходить ролі tester** | Роль tester на фазі дослідження — read-only за визначенням. Забрати Edit — не обмеження, а семантика ролі | Tester на фазі правок — це той самий агент, але тепер він змінює код. Worktree гарантує, що експерименти не впливають на main, а основна сесія залишається чистою |
| **Ризик ізоляції** | Відсутній — context isolation нічого не блокує для роботи агента, він все ще може виконати свою задачу | Вартість створення worktree (~200-500ms) + потреба синхронізації з main. Але це прийнятно для коректності роботи |

## Фаза 1 — Context isolation

**Чому read-only дослідження закривається context isolation.**

Субагент `tester` на фазі дослідження має доступ лише до Read, Grep та Bash — без Edit і Write.
Це не технічне обмеження файлової системи (як worktree), а **ізоляція на рівні опису агента**: в його дескрипції
просто перераховано дозволені інструменти. Без цього агент з усіма інструментами міг би:

- випадково зберегти нотатки прямо в коді замість повернення їх у звіті;
- створити тимчасові файли, які засмітять індексацію IDE;
- переплутати фазу дослідження з фазою правок і почати редагувати до завершення аналізу.

Оскільки `tester` на цій фазі **не призначений** для зміни коду, context isolation є природнім і достатнім
рішенням: вона нічого не забирає в агента, а лише фіксує його реальні обов'язки.

**Прив'язка до ролі tester:**
- Роль описана як «read-only research agent for the exploration phase».
- Інструменти — це контракт ролі: `tester` не редагує код, тому не має Edit/Write.
- Context isolation — це не додатковий захист, а пряма реалізація цього контракту.

## Фаза 2 — Worktree isolation

**Чому правки йдуть в окремий worktree субагента.**

Коли `tester` переходить до фази правок, він починає змінювати код — виправляти логіку eligibility
та тести. Якщо робити це в основній сесії, виникають проблеми:

1. **Незавершені зміни** — правки можуть потребувати кількох ітерацій. Між ітераціями тести на main
   залишаються зламаними.
2. **Змішування контекстів** — основна сесія може паралельно працювати з іншими завданнями.
   Чужі зміни в тій самій директорії призведуть до конфліктів.
3. **Чистота коміту** — worktree гарантує, що в коміт потраплять лише зміни, пов'язані з цим завданням.

- **Директорія worktree:** `.claude/worktrees/tester-refund`
- **Гілка:** `agent/tester-refund`

Worktree створюється перед початком фази правок і видаляється після завершення (merge + commit).
Якщо worktree залишається без змін — він автоматично прибирається.

## Підсумок вибору

**Обираємо комбіновану ізоляцію: context isolation для дослідження + worktree isolation для правок.**

Це рішення випливає з дворівневої природи завдання:

- На фазі **дослідження** агент лише читає код. Найдешевша і достатня ізоляція — обмежити його інструменти.
  Це нічого не коштує (ані часу, ані ресурсів) і точно запобігає випадковим змінам.

- На фазі **правок** агент активно змінює код. Тут потрібна справжня файлова ізоляція — worktree,
  який захищає main-гілку від незавершених змін і дозволяє безпечно працювати, не боячись зламати
  основний код.

Така комбінація дає максимальну безпеку при мінімальних накладних витратах: дослідження нічого не коштує,
а worktree створюється лише тоді, коли дійсно потрібен.

# ROLLOUT PLAN — `lint-report`

**Hook:** `lint-report`  
**Призначення:** М'який lint-сигнал за зміненим файлом  
**Тригер:** `afterFileEdit`  
**Шлях:** `frontend/src/**/*.{ts,tsx}`  
**Поточна ступінь:** `log-only`  

Цей план описує шлях розгортання одного hook — `lint-report` — від включення
в пасивний лог до повноцінної політики, яку команда автоматично виконує
через Claude Code. Кожна ступінь має мету, критерій переходу далі й recovery
path, щоб у будь-який момент можна було відкотитися без шкоди для репозиторію.

---

## Ступінь 1 — Log-only

**Мета**
Записати в лог факт редагування файлу та ім'я файлу — без жодної обробки,
без виклику зовнішніх інструментів. Переконатися, що hook працює
(не ламається, не блокує, не викидає винятків).

**Поведінка**
- `handler.command` пише один рядок у `~/.claude/logs/hooks.log`:
  `[lint-report] candidate: {{file}}`
- `handler.blocking: false`
- Команда завжди завершується з кодом 0 безвідносно до вмісту файлу.

**Критерій переходу → non-blocking**
- Hook спрацював на `afterFileEdit` щонайменше 10 разів у різних файлах.
- `hooks.log` містить усі очікувані записи.
- Жодного разу не з'явилося помилки в stderr чи коду виходу ≠ 0.
- Жоден член команди не повідомив про затримку чи збій при редагуванні.

**Recovery path**
Якщо hook не спрацьовує або падає — повернутися до перевірки конфігурації
`.claude/hooks/lint-report.json` і впевнитися, що `handler.command` не містить
помилок. На цій ступені recovery — це просто читання лога; код нічого не змінює.

---

## Ступінь 2 — Non-blocking

**Мета**
Викликати реальний linter (напр. `npx eslint`) для зміненого файлу,
але результати лише логуються — нічого не блокується й нічого не змінюється.
Зібрати статистику: скільки файлів мають помилки, які типові проблеми,
скільки часу займає перевірка.

**Поведінка**
- `handler.command` викликає `eslint --format json {{file}}`
- Результат (наявність помилок, кількість, правила) пишеться в лог.
- `handler.blocking: false`
- Команда завершується з кодом 0 — навіть якщо eslint знайшов помилки,
  сам hook не блокує.

**Критерій переходу → formatting**
- Виконано щонайменше 50 перевірок (сумарно за файлами).
- Середній час виконання eslint не перевищує 500 мс на файл.
- Статистика показує < 20 % файлів із помилками (інакше formatting буде
  надто агресивним — спочатку варто виправити наявні помилки вручну).
- Команда не генерує хибних спрацьовувань (false positives) на чистому коді.

**Recovery path**
Якщо eslint виконується довше ніж 2 секунди на файл, або якщо команда
починає заважати роботі — повернутися на `log-only` (закоментувати виклик
eslint, залишити тільки логування імені файлу).

---

## Ступінь 3 — Formatting

**Мета**
Автоматично форматувати змінений файл (через `eslint --fix` або `prettier`)
одразу після редагування, без участі людини. Результати форматування
логуються, але код форматувальника змінює файл на місці.

**Поведінка**
- `handler.command` виконує `npx eslint --fix {{file}}` і логує кількість
  виправлених проблем.
- Файл змінюється на місці (Claude Code побачить зміни при наступному зверненні
  до файлу, але не скасовує їх).
- `handler.blocking: false`
- Якщо eslint не може виправити помилку (потрібна ручна правка) — зробити
  запис у лог, не блокувати.

**Критерій переходу → test/report**
- Форматування застосовано до щонайменше 100 файлів.
- Жодного разу форматування не зламало семантику коду
  (перевіряється наявністю тестів, див. recovery).
- Середній час форматування < 800 мс на файл.
- Відсоток файлів, які eslint не може виправити автоматично, становить < 5 %.

**Recovery path**
Якщо після форматування падають тести (CI або локальний запуск) —
негайно повернутися на `non-blocking`. Зафіксувати файли, які були пошкоджені,
і додати їх в ігнор-список `eslint.ignore` або налаштувати `overrides`
у ESLint-конфігу.

## Ступінь 4 — Test/report

**Мета**
Після форматування автоматично запускати тести, що стосуються зміненого файлу
(якщо такі знайдуться), і генерувати звіт. Результат тестів впливає на
подальший діалог із Claude Code (якщо тести падають, Claude отримує
повідомлення).

**Поведінка**
- `handler.command` виконує:
  1. `eslint --fix {{file}}`
  2. Пошук тестів, пов'язаних із файлом (за паттерном `__tests__/**/*.test.ts`
     або `*.spec.ts` поряд із файлом).
  3. Запуск знайдених тестів: `npx vitest run <знайдені-тести> --reporter=json`
  4. Звіт (passed / failed / skipped) пишеться в лог.
- Результат тестів повертається як структурований JSON або текст, який
  потрапляє в контекст Claude.
- `handler.blocking: false` — Claude отримує звіт, але не блокується.

**Критерій переходу → narrow blocking**
- Тести запускалися щонайменше 30 разів.
- Середній час виконання тестів < 3 секунди.
- Хибні падіння (flaky tests) становлять < 2 % запусків.
- Claude Code коректно обробляє звіт (не ігнорує, не плутає passed/failed).
- Жоден член команди не скаржиться на уповільнення роботи.

**Recovery path**
Якщо тести виявилися надто повільними або флакають — вимкнути автоматичний
запуск тестів, залишити тільки форматування (ступінь 3). Паралельно
зафіксувати список flaky тестів і передати власникам компонентів.

Якщо Claude Code ігнорує звіт про падіння тестів — перевірити формат
виведення (можливо, він не потрапляє в контекст через структуру повідомлення).

## Ступінь 5 — Narrow blocking

**Мета**
Hook блокує редагування, якщо eslint знаходить помилки рівня `error`
(а не тільки `warning`). Блокування вузьке — стосується тільки критичних
правил (напр. `no-unused-vars`, `no-undef`, type errors).

**Поведінка**
- `handler.blocking: true`
- `handler.command` виконує `eslint --quiet {{file}}` (тільки error-level rules).
- Якщо є хоча б одна помилка рівня `error` — hook повертає код ≠ 0,
  і Claude Code не зберігає редагування.
- Якщо є тільки `warning` — hook завершується з кодом 0, але логує
  попередження.
- Форматування та тести (ступінь 4) виконуються перед блокуванням,
  щоб користувач бачив повну картину.

**Критерій переходу → policy-managed**
- Hook пропрацював у режимі narrow blocking щонайменше 2 тижні.
- За цей час сталося не більше 3 хибних блокувань (false positive —
  eslint помилився, а код валідний).
- Усі хибні блокування виправлено налаштуванням правил у `.eslintrc`.
- Жодного разу блок не спрацював на несуттєву помилку
  (напр. стилістичне зауваження).
- Члени команди підтвердили, що блокування допомагає, а не заважає.

**Recovery path**
Якщо сталося хибне блокування — виконати `git checkout -- {{file}}`
для скасування незбережених змін. Тимчасово повернути `handler.blocking: false`
і додати проблемне правило до списку винятків. Після виправлення конфігурації
повернутися на `narrow blocking`.

## Ступінь 6 — Policy-managed

**Мета**
Hook стає частиною політики команди: налаштування визначаються
в центральному конфігураційному файлі політик (policy file,
напр. `policy/lint.yaml`), який може змінюватися незалежно від коду hook.
Будь-який член команди може додавати/видаляти правила eslint без зміни
hook-скрипта.

**Поведінка**
- Hook читає список критичних правил із policy file
  (`policy/lint.yaml` або аналог).
- `handler.blocking: true`
- Якщо policy file відсутній — hook використовує дефолтний набір правил,
  зашитий у JSON-конфіг.
- Форматування, тести, звіт — як на ступені 4, але всі налаштування
  (які правила error, які warning, які тести запускати) беруться з policy.
- Зміна policy не потребує перезапуску Claude Code — hook перечитує файл
  при кожному спрацюванні.

**Критерій завершення rollout (стабільна експлуатація)**
- Policy file створено, зарев'юено й прийнято командою.
- Hook працює в режимі policy-managed щонайменше 1 місяць.
- Середня кількість блокувань на тиждень < 5 (ознака, що команда вже
  адаптувалася).
- Час від редагування до збереження (включно з eslint + тести)
  не перевищує 5 секунд у 95 % випадків.
- Не потрібно жодних ручних дій для відновлення після збою — recovery
  описано в policy file.

**Recovery path**
Якщо policy file пошкоджено або відсутній — hook автоматично переходить
у режим `narrow blocking` із дефолтними правилами, і логує попередження
про відсутність policy. Команда отримує повідомлення в лог і може
відновити policy file із git (він версіонується).

## Як просувати ступінь

1. Оновити `stage` у `.claude/hooks/lint-report.json`
2. Оновити `handler.command`, якщо ступінь вимагає іншого скрипта
3. Оновити `handler.blocking`, якщо ступінь змінює категорію
4. Записати зміну в цей ROLLOUT_PLAN (додати дату й автора)

Приклад оновлення конфігу для ступені 2:

```json
{
  "name": "lint-report",
  "stage": "non-blocking",
  "category": "non-blocking",
  "event": "afterFileEdit",
  "matcher": { "paths": ["frontend/src/**/*.{ts,tsx}"] },
  "handler": {
    "command": "scripts/lint-report-non-blocking.sh {{file}}",
    "blocking": false
  }
}
```

# TASK_SPEC.md

**Завдання:**
Скласти інженерну постановку для виправлення сортування списку повернень у support-toolbar: заявки з прапорцем `manualReview=true` мають показуватися вище за звичайні. Усередині кожної групи порядок — від новіших до старіших (за часом створення). Постановка має бути достатньою для передачі в розробку без додаткових уточнень.

**Джерело:**
[REF-482](./inputs/issue.md) — «Заявки на ручну перевірку губляться внизу списку повернень», пріоритет high, мітки: refunds, sorting, support-tools. Картка з трекера задач, містить опис поточної й очікуваної поведінки та вказівку на модуль `refunds`.

**Обсяг:**
- Аналіз issue REF-482 і перевірка гіпотези (чи справді причина в компараторі).
- Специфікація зміни сортування: композитний компаратор `manualReview` (true вище) + `createdAt` (новіші вище).
- Тест-кейс на пріоритет ручної перевірки над часом створення (регресія для REF-482).
- Оцінка впливу на суміжні компоненти (ендпойнт, support-toolbar).
- Рекомендація щодо synthetic monitoring для виявлення регресії сортування.

**Не змінювати:**
- Публічний контракт відповіді `RefundView` — використовується клієнтами support-toolbar.
- Сигнатуру методу `sortForSupport` — викликається з ендпойнта без змін.
- Архітектуру модуля `refunds` — робота обмежується логікою сортування.
- Склад залежностей і конфігурацію проєкту (Spring Boot, Gradle).
- Production-код на етапі постановки — deliverable — артефакт специфікації, а не правка.

**Перевірка:**
- Issue-аналіз підтверджує, що корінь проблеми — у компараторі `sortForSupport` (код містить лише сортування за `createdAt`). Гіпотеза перевірена зачитуванням коду.
- Специфікація подана на рев'ю команді: колега розуміє завдання без додаткових питань.
- Тест-кейс у специфікації покриває кейс "стара manualReview-заявка вище за нову звичайну".
- Synthetic monitoring: рекомендація додати перевірку, що перший елемент списку має `manualReview=true`, якщо такі є у вибірці.
- Ризик дезорієнтації агентів задокументовано з пропозицією UI-індикатора.

**Ризик:**
- **Звичка агентів:** агенти підтримки звикли до сортування лише за часом; зміна порядку може спричинити тимчасову дезорієнтацію. → Пом'якшення: додати UI-індикатор «Потребує перевірки».
- **Приховані залежності:** якщо інший компонент (наприклад, пошук або фільтр) теж сортує список незалежно, зміна в `sortForSupport` не вплине на нього. → Пом'якшення: перевірити точки сортування в модулі.
- **Регресія тестів:** новий компаратор може зламати існуючий тест часу. → Пом'якшення: існуючий тест вже перевіряє сортування за часом, і композитний компаратор зберігає цю поведінку для однорідних груп.

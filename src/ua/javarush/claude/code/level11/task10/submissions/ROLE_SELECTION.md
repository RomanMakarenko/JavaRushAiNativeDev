# Role Selection: Review Cases

## Case 1 — Готовий diff

| Поле | Значення |
|------|----------|
| **Primary role** | reviewer |
| **Review layer** | Layer 1 local review |

**Обґрунтування**: Diff уже готовий, зміна локальна, завдання — прочитати й оцінити коректність зміни до merge. Рішення ухвалюється на рівні коду до того, як зміна потрапляє в спільну гілку — це локальний review (Layer 1).

---

## Case 2 — Тест, що падає

| Поле | Значення |
|------|----------|
| **Primary role** | tester |
| **Review layer** | Verification (test correctness) |

**Обґрунтування**: Після правки тест `shouldOrderNewestFirst` падає. Потрібно з'ясувати, чи коректно тест перевіряє поведінку, і відтворити падіння в ізоляції. Рішення ухвалюється на рівні верифікації: чи правильний сам тест, чи адекватно він перевіряє очікувану поведінку.

---

## Case 3 — Незрозумілий stack trace

| Поле | Значення |
|------|----------|
| **Primary role** | debugger |
| **Review layer** | Root Cause Analysis (runtime) |

**Обґрунтування**: У логах `NullPointerException` з незрозумілим stack trace у `NotificationMapper`. Зв'язок із поточним diff неочевидний. Потрібно докопатися до першопричини — рішення ухвалюється на рівні аналізу виконання (runtime): який об'єкт null, за яких умов виникає помилка, чи пов'язана вона з поточною зміною.

---

## Case 4 — Застарілий README

| Поле | Значення |
|------|----------|
| **Primary role** | documenter |
| **Review layer** | Documentation (code-behavior alignment) |

**Обґрунтування**: `docs/notifications.md` досі стверджує "oldest first", хоча після багфікса поведінка — "newest first". Потрібно привести документацію у відповідність із фактичною поведінкою. Рішення ухвалюється на рівні документації: чи відповідає описана поведінка реальній реалізації.

---

## Review Layer vs Verification Evidence

### Review Layer — де живе рішення

Review layer — це **концептуальний рівень аналізу**, на якому ми ухвалюємо рішення. Він визначає *якого роду судження* ми виносимо:

| Case | Review Layer | Тип рішення |
|------|-------------|-------------|
| 1 | Layer 1 local review | «Чи коректна ця зміна на рівні коду до потрапляння в спільну гілку?» |
| 2 | Verification (test correctness) | «Чи правильно тест перевіряє поведінку?» |
| 3 | Root Cause Analysis (runtime) | «У чому першопричина падіння?» |
| 4 | Documentation (alignment) | «Чи опис документації відповідає коду?» |

Review layer відповідає на питання **"на якому рівні ми приймаємо рішення?"** — код, тести, виконання чи документація.

### Verification Evidence — на чому ґрунтується рішення

Verification evidence — це **конкретні артефакти та інформація**, які ми використовуємо як докази для ухвалення рішення на відповідному review layer:

| Case | Evidence | Що саме аналізуємо |
|------|----------|---------------------|
| 1 | Файли diff, стандарти коду, логіка алгоритму | Рядки коду, сигнатури, умови |
| 2 | Результати `./gradlew test`, assertions тесту | Вивід тестів, тіло тестового методу |
| 3 | Stack trace, логи, стан змінних у runtime | NPE повідомлення, стек викликів, значення null |
| 4 | Вміст файлу `docs/notifications.md` + фактична поведінка | Текст документації, реальний порядок сортування |

### Ключова різниця

| | Review Layer | Verification Evidence |
|---|---|---|
| **Питання** | *Де* ми ухвалюємо рішення? | *На чому* ми базуємо рішення? |
| **Абстракція** | Концептуальна (код / тести / runtime / docs) | Конкретна (diff, логи, stdout, текст) |
| **Змінюється** | Від типу задачі | Від конкретного артефакту |

**Аналогія**: review layer — це **суд** (кримінальний, цивільний, адміністративний), а verification evidence — це **докази** (свідчення, експертиза, документи). Суд визначає, які правила застосовувати; докази визначають, що насправді сталося.

# Project case study: Refund Tracker

## Problem

Інтернет-магазину потрібен невеликий сервіс для обліку повернень: створювати заявку на повернення та переводити її між статусами. Це навчальний capstone-проєкт, для якого після mentor review потрібно було зафіксувати не лише задум, а й фактичні перевірки, виконані виправлення та відкритий backlog. Такий фокус прямо відображений у `README.md`, `EVIDENCE.md` і `REMEDIATION.md`.

## User

Основний користувач — працівник інтернет-магазину, який опрацьовує заявки на повернення та має бачити їхній поточний стан. Другий користувач — mentor або reviewer, якому потрібні відтворювані докази роботи core flow і прозорий список того, що ще не зроблено.

## Core flow

1. Створити заявку на повернення.
2. Опрацювати заявку та змінити її статус.
3. Перевірити демонстраційний сценарій: заявка створюється і переходить у статус `approved`.
4. Підтвердити поведінку автоматичними тестами; у `EVIDENCE.md` зафіксовано результат `12 passed`.

У поточній документації цей flow названо як створення заявки та зміна її статусу. Пагінація списку заявок і сценарій уже закритої заявки свідомо винесені в backlog.

## What I owned

- Доступні артефакти не містять атрибуції особистої відповідальності за визначення меж capstone або реалізацію refund flow.
- `EVIDENCE.md` містить результати перевірок, але не вказує їхнього автора.
- `REMEDIATION.md` розділяє виконані remediation-пункти та backlog, не приписуючи їх конкретній особі.

## Verification

- `pytest -q` — команда з `README.md`; у цьому середовищі повторний запуск не виконався, оскільки команда `pytest` недоступна (`command not found: pytest`). Водночас `EVIDENCE.md` містить зафіксований результат попередньої перевірки: `12 passed`.
- `grep -R "sk-live" .` — документований secret-scan. Поточний запуск знайшов лише текстові згадки шаблону в `README.md` та `EVIDENCE.md`, а не значення ключа; `EVIDENCE.md` фіксує попередній scan без знайдених секретів.
- Ручний demo-сценарій — у `EVIDENCE.md` зафіксовано, що заявка створюється та переходить у `approved`.
- Перевірка артефактів репозиторію — прочитано `README.md`, `EVIDENCE.md`, `REMEDIATION.md`; вихідні файли проєкту не редагувалися.

## Limitations

- У поточному середовищі немає доступної команди `pytest`, тому результат `12 passed` не було повторно підтверджено.
- Документація описує core flow, але не містить повного API-контракту, схеми даних або інструкції відтворення demo-сценарію.
- Пагінація списку заявок ще не реалізована.
- Немає тесту для edge-case із уже закритою заявкою.
- Secret-scan у репозиторії документований як перевірка рядка `sk-live`; це вузький check, а не повний аналіз усіх типів секретів.

## Next steps

- Додати пагінацію до списку заявок і покрити її тестами на порожню, коротку та велику вибірку.
- Реалізувати тест і правило для спроби змінити статус уже закритої заявки.
- Додати відтворювану інструкцію запуску demo-сценарію та опис очікуваних переходів статусів.
- Розширити secret-scan перевіркою конфігураційних файлів і типових форматів токенів, не обмежуючись `sk-live`.

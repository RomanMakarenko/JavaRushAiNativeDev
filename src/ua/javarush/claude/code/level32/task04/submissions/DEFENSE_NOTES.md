# Defense Narrative — Refund Demo Service

## Крок 1. Контекст і проблема

Сапорт-агент отримує звернення клієнта щодо повернення коштів і вже має `orderId` із цього звернення. Щоб відповісти клієнту, агенту потрібні три факти: сума, валюта та поточний статус повернення, а також коротка причина.

Проблема цього сценарію — зайвий перехід до основної billing-панелі заради невеликої зведеної відповіді. Demo-сервіс дає цю відповідь одним HTTP-запитом.

## Крок 2. Основний користувацький сценарій

Основний сценарій один: агент має замовлення `A-1001` і запитує його refund summary.

1. Агент надсилає `GET /api/demo/refund-summary?orderId=A-1001`.
2. Сервіс знаходить дані цього замовлення.
3. Сервіс повертає JSON із `orderId`, сумою `49.90`, валютою `EUR`, статусом `REFUNDED` і причиною `duplicate-charge`.
4. Агент використовує ці поля у відповіді клієнту, не відкриваючи billing-панель.

У narrative я тримаюся саме цього потоку: запит за відомим замовленням → зведена відповідь → відповідь клієнту.

## Крок 3. Мета та межі рішення

Мета — показати вузький read-only endpoint для швидкого отримання refund summary за одним ідентифікатором замовлення.

У межах цього завдання є:

- обов’язковий параметр `orderId`;
- структурована JSON-відповідь;
- повернення статусу, суми, валюти та причини;
- обробка ситуації, коли замовлення не знайдене.

Поза межами цього сценарію залишаються реальна інтеграція з платіжним провайдером, автентифікація й авторизація агента та історія змін статусу.

## Крок 4. Контракт endpoint-а

Контракт має вигляд:

```http
GET /api/demo/refund-summary?orderId=A-1001
```

Успішна відповідь має містити:

```json
{
  "orderId": "A-1001",
  "amount": 49.90,
  "currency": "EUR",
  "status": "REFUNDED",
  "reason": "duplicate-charge"
}
```

Контракт важливий для захисту, бо він фіксує очікуваний результат сценарію незалежно від внутрішнього зберігання даних. Клієнту endpoint-а не потрібно знати, звідки саме сервіс узяв запис.

## Крок 5. Хід виконання та технічне рішення

Запит проходить через HTTP-рівень сервісу до пошуку refund summary за `orderId`. Для demo дані зберігаються в пам’яті, тому сервіс зосереджений на контракті та поведінці endpoint-а, а не на підключенні до зовнішньої billing-системи.

Для основного сценарію результатом є HTTP 200 і JSON із узгодженими полями. Якщо передано невідомий ідентифікатор, сервіс повертає HTTP 404 — це відокремлює відсутність замовлення від успішно знайденого refund summary.

Таке рішення достатнє для демонстрації потоку агента: вхідний `orderId` однозначно визначає вихідну коротку відповідь.

## Крок 7. Демонстрація

Демонстрація починається із запуску сервісу:

```bash
./gradlew bootRun
```

Після запуску виконується запит основного сценарію:

```bash
curl "http://localhost:8080/api/demo/refund-summary?orderId=A-1001"
```

У відповіді показуються `status: REFUNDED`, `amount: 49.90`, `currency: EUR` і `reason: duplicate-charge`. На цьому демонстрація доводить головну цінність сервісу: агент отримує коротку відповідь одним запитом.

## Крок 8. Verification

Перевірка спирається на конкретні команди та checks:

1. Запустити автоматичні тести:

   ```bash
   ./gradlew test
   ```

   Очікуваний результат — 4 зелені тести, зокрема перевірка happy path і випадку невідомого `orderId`.

2. Запустити сервіс:

   ```bash
   ./gradlew bootRun
   ```

3. Виконати ручний check основного сценарію:

   ```bash
   curl "http://localhost:8080/api/demo/refund-summary?orderId=A-1001"
   ```

   Перевірити, що JSON містить `A-1001`, `49.90`, `EUR`, `REFUNDED` і `duplicate-charge`.

4. Окремо перевірити boundary check для невідомого замовлення:

   ```bash
   curl -i "http://localhost:8080/api/demo/refund-summary?orderId=UNKNOWN"
   ```

   Очікувати HTTP 404.

Отже, verification поєднує regression check через Gradle-тести з ручною перевіркою фактичного HTTP-контракту.

## Крок 9. Limitations

1. Дані про повернення захардкожені в in-memory-сховищі, тому вони не є постійними та не надходять із реального платіжного провайдера.
2. У сервісі немає автентифікації та авторизації сапорт-агента.
3. Не реалізовано історію змін статусу повернення.
4. Навантажувальне тестування не проводилося, тому документована перевірка стосується функціонального сценарію, а не поведінки під великим навантаженням.

Ці обмеження свідомо залишені видимими: вони визначені специфікацією і не повинні маскувати demo-рівень рішення.

## Крок 10. Trade-offs / next steps

Свідомий компроміс — використати in-memory-дані замість реальної billing-інтеграції. Це спрощує демонстрацію, робить результат детермінованим і дозволяє перевірити саме контракт endpoint-а, але ціною непостійності даних і відсутності інтеграційної перевірки.

Наступним кроком була б заміна in-memory-сховища на репозиторій із чітким контрактом і підключенням до джерела refund-даних. Після цього варто додати автентифікацію та авторизацію, а також інтеграційні й навантажувальні checks. Ці зміни не входять до поточного завдання і не є частиною цього захисту.

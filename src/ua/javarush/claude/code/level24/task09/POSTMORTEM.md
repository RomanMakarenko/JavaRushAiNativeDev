# Постмортем: скидання статусу заявки під час додавання коментаря

Інцидент стосується потоку повернення коштів у Commerce OS: додавання коментаря до заявки змінювало її статус, а контролер приховував цю зміну у своїй відповіді.

## Symptom

Після `addComment` коментар зберігався, але статус `RefundRequest` у пам’яті заявки скидався з поточного значення (наприклад, `IN_REVIEW`) до `NEW`. Отже, доменний стан заявки ставав неправильним.

Контролер зберігав статус до виклику сервісу й повертав `statusBefore`. Через це HTTP-відповідь контролера виглядала правильною і маскувала помилку: клієнт бачив попередній статус, тоді як сама заявка вже мала `NEW`. Симптом був замаскований у відповіді, але не усунутий у стані системи.

## Root cause

Безпосередня причина — `request.setStatus(RefundStatus.NEW)` у `RefundCommentService.addComment`. Додавання коментаря не є переходом життєвого циклу заявки, тому сервіс не мав змінювати статус.

Symptom patch у `RefundController` (`statusBefore` і повернення збереженого значення) лише підміняє результат операції для клієнта. Він не відновлює статус у `RefundRequest`, не виправляє сервіс і створює розбіжність між відповіддю та доменним станом. Root cause fix — прибрати цей setter із `addComment` і зафіксувати інваріант: додавання коментаря не змінює статус. Після цього контролер має повертати фактичний статус заявки після виклику сервісу.

## Action + owner

- **owner: @олена** — прибрати `request.setStatus(RefundStatus.NEW)` із `RefundCommentService.addComment`, видалити symptom patch із контролера та додати регресійний тест, який перевіряє, що після додавання коментаря статус `IN_REVIEW` (і кожен інший поточний статус) зберігається.
- **owner: @максим** — додати до review-checklist обов’язкову перевірку: для кожної зміни відповіді контролера порівнювати стан ресурсу до/після операції та окремо називати root cause, а не лише видимий симптом.
- **owner: @ірена** — встановити quality gate на тести доменних інваріантів для write-операцій: тест має перевіряти не тільки побічний ефект (коментар додано), а й незмінність полів, які операція не повинна змінювати.

## Cultural takeaway

Не можна вважати інцидент виправленим лише тому, що контролер повертає очікуване значення. Відповідь API — один доказ; джерело стану та його postcondition — інший.

Workflow asset: додати до `review-checklist` пункт **«Root-cause gate: для кожної symptom patch назвати рядок, що створює симптом; перевірити postcondition у доменному стані; patch не приймається без root cause fix або документованого винятку»**. **owner: @максим**. Для write-операцій quality gate має вимагати regression test на інваріант стану. Це не дасть протягнути підміну відповіді контролера як заміну виправленню сервісу.

## Розбір за 6 принципами AI engineering culture

1. **Розробник відповідає за результат — порушено.** Відповідь контролера виглядала коректною, але результат операції в доменному стані був неправильним. Відповідальність за outcome вимагає перевіряти стан заявки, а не лише payload відповіді.

2. **Читайте diff — порушено.** У diff можна було побачити, що контролер лише запам’ятовує старий статус, а рядок, який скидає статус у сервісі, залишається. Перевірка diff мала відрізнити маскування симптома від зміни джерела дефекту.

3. **Спочатку доказ, потім довіра — порушено.** Довіру надали правильному значенню у відповіді, не перевіривши postcondition `RefundRequest.getStatus()` після виклику сервісу. Потрібні докази з тесту стану та перевірки збереженого доменного об’єкта.

4. **Спочатку root cause, потім латка — порушено.** Замість усунення `request.setStatus(RefundStatus.NEW)` додали symptom patch у контролері. Латка змінила видимість дефекту, але залишила неправильну мутацію стану.

5. **Документація збігається з кодом — порушено.** Javadoc контролера обіцяє повернути актуальний статус, але реалізація повертає snapshot до виклику сервісу. Коментарі в коді називають patch маскуванням, однак контракт контролера все одно не відповідає фактичній поведінці.

6. **Повторювані помилки виправляють workflow — порушено.** Тест перевіряв лише збереження коментаря й не захищав статусний інваріант; review-процес не вимагав розділяти root cause і symptom patch. Потрібні checklist-пункт і quality gate, описані вище.

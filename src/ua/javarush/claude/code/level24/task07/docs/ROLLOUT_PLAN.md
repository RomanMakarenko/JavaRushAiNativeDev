# План поетапного впровадження `issue-analysis`

## Current stage

Поточний етап — personal skill, який вручну використовують Andrey і пара колег. Мета пілота — перевірити, чи допомагає skill перетворювати сирий issue на структуровану постановку з блоками `Goal`, `Scope`, `Non-goals` і `Verification`, перш ніж пропонувати його як shared asset у Workflow Kit.

Впровадження відбувається **через обмежений пілот**, а не big-bang adoption:

- спочатку — контрольований пілот на трьох активних авторах issue;
- поточний personal skill і спосіб роботи команди не змінюються для решти людей;
- розширення можливе лише після вимірювання результатів і review;
- для shared asset заздалегідь визначені owner, метрики, критерії рішення та rollback.

Поза межами цього плану: зміни в коді, hooks, plugins, agents, каталогах inputs або автоматичне підключення skill усій команді.

## 3. Межі пілота

**Учасники:** Marina, Pavel і Ольга; Andrey — owner і фасилітатор.

**Тривалість:** 2 робочі тижні або щонайменше 15 нових issue сумарно (що настане пізніше). Якщо за два тижні не набрано 15 issue, фіксується недостатній обсяг даних і рішення переноситься, а не робиться за враженнями.

**Застосування:** тільки до нових issue, які створюють учасники пілота. Уже наявні issue не переписуються масово. Кожен учасник може пропустити skill для термінового або нетипового issue, зазначивши причину.

**Контрольні обмеження:**

- skill не є блокером для створення issue;
- автор зберігає фінальне редагування і відповідальність за точність;
- секрети, персональні дані та чутливий службовий контекст не вставляються у prompt/output;
- невдалий або неповний output замінюється ручним описом;
- результати пілота зберігаються як агреговані показники та приклади без зайвих чутливих даних.

## 4. Етапи та контрольні точки

### Етап 0 — baseline і готовність (до старту, 1 робочий день)

1. Andrey обирає 10–15 нещодавніх issue від трьох категорій: backend feature/task і bug report.
2. Для baseline фіксуються ті самі метрики, що й під час пілота (див. розділ 5), без вимоги переписувати історичні issue.
3. Andrey показує учасникам один приклад: сирий issue → output skill → фінальна відредагована постановка.
4. Визначається канал/таблиця обліку з датою, автором, типом issue, тривалістю та прапорцями якості. Дані доступні review-групі.
5. Перед стартом Andrey перевіряє готовність rollback і фіксує версію/копію personal skill, яку можна відокремити від shared варіанта.

**Gate 0:** якщо немає baseline, owner або журналу метрик, пілот не стартує.

### Етап 1 — обмежений пілот (2 робочі тижні)

- Marina, Pavel і Ольга застосовують skill добровільно до нових issue у своїх звичних потоках.
- Кожен output проходить короткий self-check: чи є `Goal`, `Scope`, `Non-goals`, `Verification`; чи не змінив skill факти та acceptance intent.
- Автор позначає результат як `прийнято без суттєвих змін`, `прийнято після редагування` або `відкинуто`.
- Andrey двічі на тиждень переглядає агреговані показники та 2–3 приклади на учасника. Якщо спрацьовує rollback-тригер, пілот одразу призупиняється.
- Наприкінці кожного тижня учасники дають оцінку корисності за шкалою 1–5 і вказують одну конкретну перешкоду або перевагу.

### Етап 2 — review і рішення (1 робочий день після пілота)

Review-група порівнює pilot з baseline, перевіряє якісні приклади й відповіді учасників. Andrey документує одне з рішень: `adopt`, `iterate` або `abandon`.

Рішення не означає автоматичне підключення всієї команди: воно лише визначає наступний безпечний крок.

### Етап 3 — наступна хвиля (тільки після review)

- **Після `adopt`:** додати не більше двох із п'яти людей до наступної хвилі на 1 тиждень; зберегти добровільність і ті самі метрики. Після повторного review можна пропонувати shared Workflow Kit.
- **Після `iterate`:** залишити skill у personal/пілотному режимі, внести лише погоджені зміни та повторити вимірювання з новим коротким пілотом. Інших п'ятьох не підключати.
- **Після `abandon`:** припинити пілот і повернутися до звичайного процесу; не переносити skill у shared Workflow Kit.

Будь-яке рішення про shared asset фіксується у `CHANGELOG.md` і проходить командний review. У межах цього завдання ці файли не змінюються.

## Success metrics

Метрики збираються на рівні окремого issue і звітуються агреговано за учасником та типом issue. Порівнюються з baseline; сам факт використання skill не вважається успіхом.

| Метрика | Як спостерігати | Ціль/сигнал |
|---|---|---|
| **Час до готової постановки** | хвилини від початку оформлення до стану, коли issue можна віддати на review; однаковий спосіб вимірювання для baseline і pilot | медіана не гірша за baseline та бажано на ≥20% нижча |
| **Повнота структури** | частка issue, де присутні й змістовно заповнені всі 4 блоки: `Goal`, `Scope`, `Non-goals`, `Verification` | ≥90% pilot issue |
| **Частка суттєвого ручного перероблення** | частка issue, де автор переписав основну частину output або відкинув його; позначка + коротка причина | ≤25%; зростання проти baseline — сигнал iterate |
| **Прийняття output** | частка issue, прийнятих без суттєвих змін або після малих правок | ≥75% як практично придатні |
| **Уточнення після review** | кількість/частка issue, для яких reviewer просить уточнити мету, межі або перевірку | не гірше baseline; бажано зменшення ≥20% |
| **Дефекти якості** | count випадків, коли skill додав вигаданий факт, втратив важливе обмеження або зробив `Verification` непридатним | 0 критичних; будь-який критичний — негайна пауза й triage |
| **Досвід автора** | коротка оцінка 1–5 після використання та текстовий коментар | середня оцінка ≥4/5, без повторюваної нерозв'язаної скарги |
| **Реальне використання** | кількість issue, для яких skill фактично застосували, і частка добровільного пропуску з причиною | ≥15 issue; пропуски аналізуються, але не караються |

### Мінімальний журнал спостереження

Для кожного pilot issue достатньо зафіксувати: дату, роль автора, тип issue, baseline/pilot, час, статус прийняття, повноту 4 блоків, факт суттєвого редагування, кількість уточнень, дефект якості (так/ні), оцінку 1–5 і коротку причину пропуску/відкидання.

## Decision options після review

### `adopt` — обережно розширювати

Обирається, якщо виконані всі умови:

- набрано щонайменше 15 pilot issue;
- немає критичного дефекту якості;
- повнота структури ≥90%, практичне прийняття ≥75%, середня оцінка ≥4/5;
- медіанний час не погіршився, а метрика уточнень не стала гіршою за baseline;
- жоден учасник не повідомив про невирішений блокер.

Дія: перейти до наступної хвилі максимум із двох людей, зробити review і лише потім ухвалювати окреме рішення про shared Workflow Kit. Загальне підключення всіх дев'ятьох не є автоматичним наслідком `adopt`.

### `iterate` — змінити й повторити пілот

Обирається, якщо критичних дефектів немає, але одна чи більше цільових метрик не досягнуті або є повторювана якісна проблема. Andrey формує короткий список змін, визначає очікуваний ефект і повторює пілот на тій самій групі або максимум на одному додатковому учаснику.

Зміни не розгортаються як shared asset до нового review. Якщо після однієї ітерації критерії все ще не виконані, review-група окремо переглядає доцільність `abandon`.

### `abandon` — припинити просування

Обирається, якщо є критичний дефект, учасники не отримують практичної користі, adoption залишається низьким після повторної спроби або витрати на редагування перевищують користь. Skill не переноситься до shared Workflow Kit; команда повертається до звичайного оформлення issue, а висновок фіксується для майбутнього review.

## 7. Rollback path

Rollback може ініціювати Andrey негайно, якщо виявлено критичний дефект, витік чутливого контексту, систематичне спотворення вимог або різке погіршення часу/якості. Будь-який учасник може попросити паузу через owner; до з'ясування причин нове використання припиняється.

**Послідовність rollback:**

1. Andrey оголошує `pilot paused` у каналі обліку та позначає affected issue для ручного review.
2. Учасники припиняють подавати нові issue через skill; термінові issue оформлюють звичайним способом.
3. Вимкнути asset: видалити каталог `.claude/skills/issue-analysis/`, як передбачено способом вимкнення skill. Якщо до цього моменту створено shared-копію, спочатку відкликати її підключення та повернути попередню версію через review; копію не видаляти без окремої перевірки та погодження. Після вимкнення відновлюється звичайний workflow автора.
4. Andrey перевіряє останні output на фактичні помилки та передає власникам issue перелік тих, що потребують ручного виправлення.
5. Протягом 1 робочого дня owner фіксує причину, affected issue, результат перевірки та рішення `iterate` або `abandon`. Для shared asset rollback і його причину заносять у `CHANGELOG.md` через звичайний review-процес.
6. Повторний запуск дозволений лише після усунення підтвердженої причини, оновлення критеріїв перевірки й нового короткого approval review-групи.

Rollback не передбачає масового переписування вже створених issue: виправляються тільки конкретні affected issue, а решта залишається без змін. Резервний процес — ручне оформлення issue — доступний постійно, тому команда не залежить від skill.

## 8. Критерій завершення плану

План вважається виконаним після того, як Andrey має журнал baseline/pilot, review-група перевірила порогові метрики та приклади, а обраний шлях (`adopt`, `iterate` або `abandon`) зафіксований із owner і rollback path. До цього моменту решта команди не підключається.

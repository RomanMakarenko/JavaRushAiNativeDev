# Аналіз вакансії Backend Engineer (Java) — Nimbus Payments

## Must-have

Вимоги, які вакансія прямо називає обов’язковими:

- Комерційний досвід роботи з Java від 2 років.
- Spring Boot і побудова REST API.
- Реляційні бази даних, зокрема PostgreSQL, та впевнений SQL.
- Git і pull request workflow: робота з гілками, code review і merge.
- Unit- та integration-тести на JUnit.

## Nice-to-have

Навички, які вакансія визначає як перевагу, але не як обов’язкову вимогу:

- Docker і контейнеризація сервісів.
- CI/CD, наприклад GitHub Actions.
- Черги повідомлень: Kafka або RabbitMQ.
- Спостережуваність: логування та метрики.
- Написання зрозумілої технічної документації.

## Responsibilities

- Розробляти та підтримувати backend-сервіси на Java і Spring Boot.
- Вести завдання в issue-to-PR циклі: розбір, реалізація, code review, merge.
- Покривати зміни тестами та підтримувати надійність платіжного flow.
- Брати участь у покращенні внутрішніх інструментів команди.

## Stack

Стек і технічні практики, прямо згадані у вакансії:

- Java.
- Spring Boot.
- REST API.
- PostgreSQL і SQL.
- Git та pull request workflow.
- JUnit для unit- та integration-тестів.
- Docker — як бажана навичка.
- CI/CD, зокрема GitHub Actions — як бажана навичка.
- Kafka або RabbitMQ — як бажана навичка.

## Seniority signals

- Прямий рівневий маркер: вакансія очікує від 2 років комерційного досвіду на Java.
- Обсяг відповідальності передбачає самостійне проходження workstream від issue до PR.
- Від кандидата очікується участь у розборі завдання, реалізації, code review та merge.
- Очікується відповідальність за тестове покриття змін і надійність платіжного flow.
- У вакансії згадані ownership і швидке зростання як цінності команди.
- Формат роботи — розподілена команда та remote.
- Для роботи потрібна англійська на рівні читання технічної документації.

## Hidden signals

Це інтерпретації, а не прямі вимоги вакансії; кожна позначена як hypothesis:

- **Hypothesis:** згадка про refund flow, підписки та білінг означає, що для команди важливі уважність до коректності змін і стабільності платіжних сценаріїв.
- **Hypothesis:** формулювання «команда, яка володіє своїм workstream від issue до PR» може означати очікування самостійності без постійного покрокового супроводу.
- **Hypothesis:** повторення issue-to-PR циклу в описі команди та responsibilities може означати, що практичний Git/PR-процес є важливішим за знання Git лише на рівні окремих команд.
- **Hypothesis:** згадка про швидке зростання може означати готовність поступово розширювати відповідальність, але вакансія не визначає конкретний план розвитку.
- **Hypothesis:** розподілений remote-формат може означати потребу чітко комунікувати статус і залишати зрозумілі артефакти роботи, хоча окремої вимоги до комунікаційних практик немає.

## Red flags

- Комерційний досвід кандидата на Java близько 1,5 року, тоді як у вакансії прямо вказано мінімум 2 роки — це невідповідність must-have.
- Integration-тести в доказах кандидата виконувалися обмежено, лише в одному модулі. Це слабше за пряме очікування unit- та integration-тестів на JUnit і потребує перевірки глибини досвіду.
- Для Kafka/RabbitMQ у кандидата є лише теоретичні знання без бойового досвіду. Це не порушення must-have, але відсутність доказу одного з nice-to-have.
- Observability підтверджена лише логуванням; доказів налаштування метрик немає. Це часткове покриття nice-to-have.
- У банку доказів немає окремого артефакту з технічною документацією, тому відповідність цьому nice-to-have не підтверджена.

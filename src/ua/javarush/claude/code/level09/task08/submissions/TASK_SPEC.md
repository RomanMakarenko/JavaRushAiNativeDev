# TASK_SPEC: BILL-218 — повторне списання при ретраї оплати

## Goal

Запобігти повторному списанню коштів, коли на один і той самий рахунок надходить більше одного платіжного запиту в межах вікна ретраю (таймаут клієнта, повторне натискання «Оплатити», автоматичний retry з мобільного застосунку).

## Scope

- **Що робимо**: додаємо ідемпотентність у `BillingService.charge(...)` — перед створенням платежу у зовнішнього провайдера перевіряємо, чи вже був успішний платіж за цим рахунком.
- **Де робимо**: тільки серверний код у `BillingService` (або шар над ним). Жодних змін у мобільному застосунку чи фронтенді.
- **Що НЕ робимо**:
  - Не змінюємо сигнатуру або поведінку `POST /api/billing/charge`.
  - Не чіпаємо логіку повернень (`refund`).
  - Не переписуємо платіжний шар (інтеграцію з провайдером).

## Constraints

- Зворотна сумісність HTTP-ендпоінта `POST /api/billing/charge` — клієнти не змінюють свої запити.
- Зміни мають вкластися в поточний релізний цикл — ніякого великого рефакторингу.
- Механізм ідемпотентності має працювати атомарно (блокувати race condition між паралельними запитами на один рахунок).

## Verification

1. Відправити два однакових запити на оплату рахунку з інтервалом < 1 с.
   - Очікується: один успішний платіж, другий запит повертає відповідь без створення нового платежу.
2. Відправити запит на оплату вже оплаченого рахунку через 5 хв.
   - Очікується: другий запит не створює платіж, користувач не бачить помилки.
3. Існуючі тести на `POST /api/billing/charge` продовжують проходити.

# TASK SPEC

## Goal
Запити на повернення в Refund Inbox сортуються спочатку за пріоритетом (від високого до низького), усередині однакового пріоритету — від найстаріших до найновіших за датою створення.

## Scope
Серверне сортування в `RefundInboxService.java` (level02/task01). Ймовірно, буде зачеплено:
- `src/.../level02/task01/.../shop/refund/RefundInboxService.java` — поточна логіка сортує лише за `createdAt`, потрібно додати `priority`;
- `src/.../level02/task01/.../shop/refund/RefundRequest.java` — можливо, додати поле `priority` (якщо його немає);
- Тести сортування (unit-тести на `RefundInboxService`).

Фронтенд не змінюється — список надходить із бекенда вже відсортованим.

## Non-goals
- Не змінюємо фронтенд Refund Inbox.
- Не змінюємо схему БД (якщо пріоритет зберігається окремо — припущення).
- Не змінюємо REST API контракт модуля підтримки.
- Не рефакторимо `RefundController` чи `RefundPolicyService` (рівень billing/decision).

## Acceptance criteria
- Запити з вищим `priority` відображаються раніше за нижчі;
- У межах однакового `priority` запити впорядковані за зростанням `createdAt`;
- Поточний тест `sortByOldestFirst` змінюється на новий тест із пріоритетним сортуванням;
- Усі існуючі тести модуля підтримки залишаються зеленими.

## Verification
- Unit-тест на `RefundInboxService` із різними комбінаціями priority + createdAt.
- Запуск тестів: `./gradlew test` або `mvn test` (залежно від збірки проєкту).

## Open questions
- Чи має `RefundRequest` уже поле `priority`? Якщо ні — який тип і діапазон значень (int 1–5, enum, тощо)?
- Який напрямок сортування priority вважається «високим» — більше число чи менше?
- Чи потребує стабільний порядок додаткового критерію (наприклад, `id`) за однакових `priority` та `createdAt`?
- Де зберігається/обчислюється priority — у таблиці БД чи обчислюється на льоту?

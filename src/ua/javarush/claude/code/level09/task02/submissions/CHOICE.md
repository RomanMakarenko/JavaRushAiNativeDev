# Чому rule, а не CLAUDE.md або skill

## Варіант: CLAUDE.md (глобальний файл на рівні проєкту)

CLAUDE.md завантажується в контекст при **кожному** запиті, незалежно від
того, з якими файлами працює Claude. Вимоги до документації (виконуваність
команд, формат блоків, актуальність) потрібні **тільки** коли мова йде про
файли в `docs/`. Додавати їх у CLAUDE.md означало б:

- Займати контекст на завданнях, де документація взагалі не згадується.
- Порушувати принцип найменших привілеїв для інструкцій.

## Варіант: skill (інвокована здібність)

Skills призначені для **активних, багатокрокових процедур** — "перевірити PR",
"запустити тести", "зробити реліз". Вимога "команди в документації мають бути
виконуваними" — це **пасивне обмеження**, яке має автоматично діяти щоразу,
коли Claude читає або редагує файли документації.

Крім того, skill треба **явно викликати** (через `/docs-review` або
`@docs-review`). Це не підходить для правила, яке має спрацьовувати
автоматично.

## Варіант: scoped rule (вибрано)

Scoped rule (`docs-review`) задовольняє обидві вимоги:

| Вимога | Як виконується |
| --- | --- |
| **Автоматичність** | Claude Code активує правило, коли в поточному запиті є файли, що відповідають `glob: "docs/**"`. |
| **Відсутність у нерелевантних завданнях** | Правило не завантажується в контекст, поки користувач не працює з документацією. |
| **Пасивна природа** | Це набір вимог і обмежень, а не процедура з кроками. |

## Підсумок

- **CLAUDE.md** — занадто глобальний, засмічує контекст.
- **Skill** — потребує явного виклику, не підходить для пасивних обмежень.
- **Scoped rule** — автозавантаження за потребою + пасивний режим. Саме те, що
  потрібно для правил перевірки документації.

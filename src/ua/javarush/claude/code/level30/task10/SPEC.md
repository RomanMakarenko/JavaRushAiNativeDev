# SPEC.md — Refund Assistant (фрагмент для reviewer'а)

> Зробіть другий прохід по чорновику: доведіть три розділи нижче до
> reviewer-ready стану. Reviewer має за п'ять хвилин зрозуміти, як
> перевірити core flow, що він побачить на demo і про яке обмеження ви
> чесно попереджаєте. Код і тести не чіпайте.

## План перевірки

1. У корені задачі запустіть demo-сервер:
   ```bash
   uvicorn app.main:app --host 127.0.0.1 --port 8080
   ```
2. В іншому терміналі, залишаючись у цій самій робочій директорії, виконайте GET-запит до актуального endpoint:
   ```bash
   curl -i http://127.0.0.1:8080/api/demo/status
   ```
3. Перевірте, що відповідь має HTTP-код `200` і JSON з такими ключовими полями:
   - `artifactType` дорівнює `"demo"`;
   - `sampleDataLoaded` дорівнює `true`;
   - `coreFlow` описує перевірку refund за id заявки та рішення з причиною.
4. Після перевірки зупиніть demo-сервер (`Ctrl+C`). Успішне виконання цих кроків підтверджує core flow demo через `/api/demo/status`.

## Demo-сценарій

1. Відкрийте два термінали в корені задачі та в першому запустіть demo-сервер командою `uvicorn app.main:app --host 127.0.0.1 --port 8080`.
2. У другому терміналі продемонструйте актуальний verification path: виконайте `curl -i http://127.0.0.1:8080/api/demo/status`.
3. Разом із reviewer'ом перевірте результат: HTTP `200`, `artifactType: "demo"`, `sampleDataLoaded: true`, а також `coreFlow` про перевірку refund за id заявки й рішення з причиною.
4. Завершіть демонстрацію, зупинивши сервер через `Ctrl+C`. Цей сценарій повторює кроки ручного плану без переходу на застарілий endpoint.

## Відомі обмеження

`smoke-demo.sh` звертається до застарілого `GET /api/refund/check`, тоді як актуальний endpoint demo, визначений у `app/main.py`, — `GET /api/demo/status`. Тест `tests/test_smoke_script.py` також фіксує старий шлях, тому smoke-перевірка наразі не є надійним verification path для поточного core flow. До виправлення verification path проходить вручну за наведеним вище планом, повз smoke-скрипт; правку скрипта й тесту відкладено у фазу реалізації.

Див. запис-слід у `EVIDENCE_LOG.md` щодо цієї розбіжності.

# MVP specification

## Problem
Агенту підтримки першої лінії потрібно швидко зрозуміти, чи можна повернути гроші за конкретною заявкою. Без компактної перевірки рішення доводиться приймати вручну, що сповільнює обробку звернення.

## Target user / JTBD
**Користувач:** агент підтримки першої лінії.

**JTBD:** отримати за ID заявки одне зрозуміле рішення щодо refund — `allow`, `deny` або `manual` — разом із причиною.

MVP не призначений для клієнта або фінансового відділу.

## MVP scope
- Demo-status endpoint: `GET /api/demo/status`.
- Автоматичне завантаження синтетичних sample data під час старту demo-профілю.
- Demo-фікстура з 12 заявками.
- Одна перевірка refund за ID заявки.
- Результат перевірки: `allow`, `deny` або `manual` і текстова причина.
- У відповіді demo-status доступні ознаки demo-режиму, завантаження sample data та опис основного flow: `artifactType=demo`, `sampleDataLoaded`, `coreFlow`.

## Non-goals
- Реальна інтеграція з білінгом.
- Авторизація та розмежування доступу.
- Історія рішень.
- Повноцінна refund-політика або її налаштування через UI.
- Використання реальних клієнтських чи платіжних даних.

## Core user flow
1. Агент запускає demo-профіль.
2. Система автоматично завантажує синтетичні sample data.
3. Агент передає ID заявки до refund check.
4. Система повертає одне з рішень `allow`, `deny` або `manual` та причину.
5. Агент використовує результат як підказку для подальшої обробки звернення.

## Success metric
Під час demo-перевірки для кожної валідної заявки результат refund check формується за один виклик і містить рівно одне рішення (`allow`, `deny` або `manual`) та непорожню причину. Метрика вимірюється smoke-перевіркою та ручною перевіркою одного sample ID; це критерій готовності MVP, а не твердження про production-результати.

## Acceptance criteria
- `GET /api/demo/status` доступний у demo-профілі та повертає `artifactType=demo`.
- Після старту demo-профілю поле `sampleDataLoaded` сигналізує, що sample data завантажені.
- Demo-фікстура містить 12 синтетичних заявок.
- Refund check приймає ID заявки та повертає лише одне з рішень `allow`, `deny`, `manual` разом із reason.
- Основний flow refund check відображений у полі `coreFlow` відповіді demo-status або в еквівалентному demo-контракті.
- MVP не викликає реальний білінг, не вимагає авторизації та не зберігає історію рішень.
- Smoke-команда завершується успішно без внесення змін до `inputs/`.

## Verification plan
1. Запустити штатну перевірку demo:
   ```bash
   bash scripts/smoke-demo.sh
   ```
   Очікування: команда завершується з exit code `0` і перевіряє `GET /api/demo/status`.
2. Перевірити відповідь demo-status через HTTP check:
   ```bash
   curl -fsS http://localhost:<demo-port>/api/demo/status
   ```
   У відповіді перевірити `artifactType=demo`, ознаку `sampleDataLoaded` та `coreFlow`.
3. Взяти один ID із demo-фікстури та виконати refund check; перевірити, що відповідь містить одне з `allow`/`deny`/`manual` і непорожній `reason`.
4. Переконатися, що вхідні чорновики не змінені:
   ```bash
   git diff --exit-code -- inputs/
   ```
5. Переглянути фінальний diff документа:
   ```bash
   git diff -- submissions/MVP_SPEC.md
   ```

## Demo scenario
1. Запустити demo-профіль.
2. Виконати `bash scripts/smoke-demo.sh`.
3. Показати відповідь `GET /api/demo/status` із `artifactType=demo` і завантаженими sample data.
4. Передати ID однієї sample-заявки до refund check.
5. Показати рішення `allow`, `deny` або `manual` та його причину.

## Risks
- Жорстко закодована refund-політика може не відповідати майбутнім бізнес-правилам.
- Синтетичні sample data не покривають усі реальні варіанти заявок.
- Відсутність авторизації робить demo непридатним для відкритого production-використання.
- Без історії рішень складно відтворити попередню перевірку.

## Known limitations
- Дані в demo синтетичні; висновки з них не підтверджують поведінку на production-даних.
- Refund-політика жорстко закодована й не налаштовується користувачем.
- MVP не інтегрований із реальним білінгом.
- Авторизація та історія рішень відсутні.

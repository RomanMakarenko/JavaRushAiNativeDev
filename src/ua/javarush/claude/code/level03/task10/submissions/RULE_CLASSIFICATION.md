# Класифікація правил

## Project-wide (загальнопроєктні правила)

Правила, що діють на весь кодовий масив і всі задачі в репозиторії.

| № | Правило | Чому Project-wide |
|---|---------|-------------------|
| 1 | У production-коді не повинно бути `console.log` | Стосується **будь-якого** файлу в репозиторії, не прив'язане до конкретної задачі. Загальна вимога якості коду. |
| 3 | Усі коміти мають проходити pre-commit hook з лінтером | Діє на **кожен коміт** незалежно від задачі — це інфраструктурне налаштування репозиторію. |
| 5 | Кожен PR проходить CI-перевірку із зеленими тестами перед merge | Процесне правило для **всіх PR** у проєкті, не тільки для цього рефанду. |
| 6 | Не додавати нові runtime-залежності в проєкт | Проєктна політика керування залежностями — діє на всі задачі, аби не роздувати бандл. |
| 9 | Будь-який код форматувати через загальний formatter проєкту | Узгоджений стиль коду — вимога до **всіх файлів**, незалежно від автора чи задачі. |
| 11 | Гілка має бути захищена branch protection rule (без прямого push у main) | Налаштування репозиторію (GitHub Settings), діє на **весь проєкт**, а не на конкретну гілку задачі. |
| 12 | Усі секрети зберігаються лише в `.env`, не в коді | Політика безпеки, що діє на **весь кодовий масив** — не можна хардкодити токени ніде і ніколи. |

## Task-specific (правила, що діють лише в межах задачі)

Правила, які стосуються виключно поточної задачі «додати поле `notes` у refund flow» і не обов'язкові для інших задач.

| № | Правило | Чому Task-specific |
|---|---------|-------------------|
| 2 | Ліміт довжини `notes` у цій задачі — рівно 1000 символів | Числовий ліміт, визначений **виключно для цієї задачі**. В іншій задачі ліміт може бути іншим або поле взагалі не існувати. |
| 4 | Public refund API response у цій задачі змінювати не можна | Обмеження, що стосується **лише scope задачі** — зміна refund API. В інших задачах API може змінюватися. |
| 7 | У цій задачі не можна редагувати наявні SQL-міграції | Правило для **конкретного набору файлів (міграцій)** у контексті цієї задачі. Інші задачі можуть додавати нові міграції. |
| 8 | (try) Не чіпати auth module під час редагування refunds | Обмеження на **дотичність модулів** — актуальне лише поки ми працюємо над refund-задачею. ⚠️ Див. розділ нижче. |
| 10 | Diff цієї задачі має залишатися маленьким і reviewable | Вимога до **обсягу змін у цьому конкретному PR**. Не загальне правило — для великих рефакторингів diff може бути великим. |

---

## Enforcement (правила, які вже автоматизовані або мають бути)

Правила, контроль виконання яких покладено на інструменти (лінтери, хуки, CI, GitHub Settings), а не на пам'ять розробника.

| № | Правило | Чому Enforcement |
|---|---------|-----------------|
| 1 | У production-коді не повинно бути `console.log` | **Вже автоматизоване**: eslint-правило `no-console` або аналог. Людина не мусить пам'ятати — лінтер не пропустить. |
| 3 | Усі коміти мають проходити pre-commit hook з лінтером | **Вже автоматизоване**: git hook (`lint-staged`, `husky`) блокує коміт, якщо лінтер падає. |
| 5 | Кожен PR проходить CI-перевірку із зеленими тестами перед merge | **Вже автоматизоване**: GitHub Actions / CI-пайплайн блокує merge, якщо тести червоні. |
| 9 | Будь-який код форматувати через загальний formatter проєкту | **Вже автоматизоване** (або має бути): pre-commit hook з Prettier/ESLint `--fix` + editorconfig. |
| 11 | Гілка має бути захищена branch protection rule (без прямого push у main) | **Вже автоматизоване**: налаштовується в GitHub Settings один раз і діє без участі розробника. |
| 12 | Усі секрети зберігаються лише в `.env`, не в коді | **Має бути автоматизоване**: secret scanner (truffleHog, GitLeaks) у CI, або рев'ю-чекліст, який перевіряється автоматично. |

**Важливо:** Правила 1, 3, 5, 9, 11, 12 потрапляють одночасно до **Project-wide** (за змістом) і до **Enforcement** (за механізмом контролю) — це не помилка, а перетин ортогональних категорій: *де діє* (scope) vs *як контролюється* (automation).

Правила 2, 4, 7, 10 з категорії **Task-specific** поки що не автоматизовані — їх дотримання забезпечується code review. Правило 6 (залежності) теж не автоматизоване — можна додати `dependency-review` у CI.

## Проблемне формулювання: правило №8

**Текст:** "Try not to touch the auth module while editing refunds."

**Чому це проблема:**

Словосполучення *"try not to"* — це **рекомендація, а не заборона**. Розробник може:

- "спробувати не чіпати", але якщо рефакторинг потребує зміни в auth — технічно він не порушує правило, бо "try" не гарантує результату;
- випадково імпортувати щось із auth і виправдати це тим, що "I tried not to";
- у code review неможливо апелювати до "try" — це не чіткий критерій.

**Висновок:** М'яке формулювання **не годиться** для жорсткого обмеження. Правило має стати **строгим** (залишається в Task-specific) із чіткою редакцією:

> **8'. У межах цієї задачі заборонено змінювати файли з модуля `auth/`.** Якщо зміна в auth необхідна — створити окрему задачу.

**Додатковий технічний контроль (опціонально):** додати в CI перевірку, що `git diff --name-only` не містить шляхів з `auth/` у цьому PR, або налаштувати CODEOWNERS, щоб зміни в `auth/` автоматично запитували апрув від окремої команди.

# Minimal Prototype Decision — team-review-kit

**Дата:** 2026-07-06  
**Артефакт:** `draft-plugin/` — `team-review-kit (draft)`  
**Мета:** Визначити склад першого **minimal team-ready prototype** (v0.1.0), який можна віддати команді в роботу вже зараз. Рішення базується на готовності кожного компонента до реального використання в командному review-процесі, а не на загальному страху перед розширеннями.

---

## Keep in v0.1.0

### `plugin.json` — маніфест плагіна
**Чому входить:**
- Точка входу, без якої жоден компонент не завантажиться
- Для v0.1.0 реєструє лише два skills, без зайвих посилань на відкладені компоненти

### `README.md` — документація проєкту
**Чому входить:**
- Пояснює призначення та склад прототипу новим членам команди
- Фіксує рішення про обмежений обсяг — команда розуміє, що саме входить у v0.1.0 і що буде пізніше

### `skills/issue-analysis` — аналіз задач
**Чому входить:**
- Має чіткий контракт: вхід (текст issue + пов'язані файли) → вихід (структурований task spec: goal, current behavior, desired behavior, scope, non-goals, open questions)
- Вимагає лише `read-only` інструменти — безпечний для будь-якого репозиторію
- Самодостатній: не залежить від інших компонентів пайплайну
- Вирішує реальну командну потребу: перетворити неструктурований баг-репорт або фічу-реквест на задачу, готову до роботи

### `skills/pr-review` — перегляд PR
**Чому входить:**
- Має чіткий контракт: вхід (diff) → вихід (список ризиків, спірних місць, відсутніх перевірок, резюме для PR-опису)
- Вимагає лише `read-only` інструменти
- Самодостатній
- Разом з `issue-analysis` формує замкнений review-пайплайн: задача → код → перегляд. Команда отримує цілісний процес без зовнішніх залежностей

## Exclude for now

### `hooks/format-on-edit` — автоформатування Java
**Чому виключається з v0.1.0:**
- Для team-ready prototype не є критичним: команда може форматувати код вручну або через IDE
- Посилається на обробник `run-formatter`, якого не існує — для введення в прототип знадобиться обрати форматер, налаштувати правила, протестувати на реальному коді
- Успішний review-пайплайн не залежить від автоформатування — це окрема зручність, а не частина review-процесу

### `mcp/issue-tracker` — інтеграція з трекером задач
**Чому виключається з v0.1.0:**
- Це заглушка: відсутні команда для запуску сервера, аутентифікація, протокол обміну
- Для team-ready prototype інтеграція із зовнішнім сервісом потребує вибору конкретного трекера, налаштування OAuth-потоку, обробки мережевих помилок — це окремий проєкт, не готовий до включення
- Локальний review-пайплайн (issue → review) працює без трекера задач

### `agents/auto-reviewer` — автономний рев'юер
**Чому виключається з v0.1.0:**
- Позначений як незавершений: "Not brought to a full contract, needs separate work on roles, permissions, and output contract"
- Для team-ready prototype потрібні чіткі roles, permissions та output contract — усього цього немає
- Його функціональність частково перекривається `pr-review` skill, який входить у v0.1.0. Спочатку команда має освоїти ручний review через skill, а автоматизація додається пізніше, коли стане зрозуміло, які саме кроки варто автоматизувати

## Підсумок

**v0.1.0 — це мінімальний team-ready prototype, який дає команді цілісний review-пайплайн:**

```
Джерело (issue/задача) → issue-analysis (структурує) → код → pr-review (перевіряє)
```

Усе всередині цього пайплайну:
- Працює на `read-only` інструментах — безпечно для будь-якого репозиторію
- Не потребує зовнішніх сервісів, токенів або auth-конфігурації
- Кожен компонент самодостатній і готовий до використання негайно

Відкладені компоненти (`hooks`, `mcp`, `agents`) не викидаються — вони фіксуються як наступні ітерації після того, як команда почне реально використовувати базовий пайплайн і сформулює конкретні больові точки для автоматизації.

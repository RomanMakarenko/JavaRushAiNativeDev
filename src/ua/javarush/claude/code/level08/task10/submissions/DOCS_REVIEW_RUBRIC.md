# Docs-as-Code Review Rubric

Цей рубрикатор призначений для рецензування документації, яка ведеться як код (docs-as-code):
документ — це файл у репозиторії, зміни проходять через Pull Request, а рецензент перевіряє
їх за тими ж принципами, що й код.

---

## Criteria

### accuracy

**Reviewer question:** Чи відповідає описана поведінка фактичній реалізації (версії залежностей,
формати даних, сигнатури методів, URL, назви класів/ендпоінтів)?

Перевіряйте кожен технічний факт: якщо документ каже «метод повертає 201», а код повертає 200 —
це помилка. Якщо не впевнені — позначте як `needs verification` у коментарі.

### source-anchored

**Reviewer question:** Чи кожне твердження про поведінку системи підкріплене посиланням на
конкретний файл, рядок коду, тест, скріншот, або інший авторитетний джерельний артефакт?

Документація не повинна містити «сирих» тверджень без якоря. Для docs-as-code прийнятними
якорями є: шлях + рядок у вихідному коді, назва тесту, посилання на коміт, зовнішній
стандарт (RFC, специфікація), або скріншот UI з датою. Відсутність якоря — це finding.

### complete enough

**Reviewer question:** Чи покриває документ усі суттєві варіанти поведінки, крайові випадки
(edge cases), стани помилок і наслідки для суміжних модулів, які читач очікував би знайти?

Недостатня повнота — це коли читач, слідуючи документу, може потрапити в ситуацію, не
описану в жодному розділі (наприклад: «що станеться, якщо токен прострочений?» — а в
документі тільки happy path).

### no hallucinations

**Reviewer question:** Чи містить документ будь-які твердження, які неможливо підтвердити
наявним кодом, тестами, або зовнішніми джерелами (вигадані API, неіснуючі параметри,
поведінка, якої ніколи не було)?

Халюцинація відрізняється від неточності: неточність — неправильне значення існуючого факту;
халюцинація — факт, якого не існує в принципі. Будь-яка халюцинація є блокуючим finding-ом.

### commands checked

**Reviewer question:** Чи всі команди (термінальні, SQL, HTTP-запити, docker, make, gradle/npm)
у документі були виконані й дали саме той результат, який описано?

Якщо команда не запускалась рецензентом або автором у середовищі, тотожному до цільового,
вона має бути позначена як `unverified`. Снапшот виводу (якщо наведений) має збігатися
з реальним виводом команди в момент написання документа.

### assumptions listed

**Reviewer question:** Чи явно перелічені всі припущення, від яких залежить коректність
документа (версія середовища, наявність зовнішніх сервісів, права доступу, попередньо
встановлені інструменти, стан бази даних)?

Приховані припущення — часта причина, чому документ працює в автора і не працює в читача.
Кожне припущення має бути в окремому маркованому пункті на початку документа або відповідного
розділу.

### limitations included

**Reviewer question:** Чи задокументовані обмеження описаного підходу або інструкції
(незворотні операції, деградація продуктивності, сумісність лише з певними версіями,
відсутність підтримки певних сценаріїв)?

Якщо рішення має trade-offs, а документ їх не згадує — це вводить в оману. Limitations
мають бути в окремому розділі та не суперечити іншим частинам документа.

### diff reviewable

**Reviewer question:** Чи можна зрозуміти суть змін, переглядаючи лише diff (без відкриття
файлів кодованими шляхами, без бінарних вкладок, без нерелевантних або глобальних змін
форматування)?

Для docs-as-code diff — основний інструмент рецензента. Якщо diff містить:
- зміни в незв'язаних файлах;
- масова зміна форматування (пробіли, перенесення рядків);
- бінарні артефакти (зображення, PDF);
— рецензент має право відхилити зміну та попросити автора розділити на атомарні коміти.

## First pass procedure

Мета першого проходу — швидко відсіяти зміни, які не готові до повноцінної перевірки.

1. **Перевірте, чи diff reviewable.** Якщо diff містить бінарні файли, масове переформатування,
   або зміни в незв'язаних модулях — зупиніться та позначте `needs split` з поясненням.
2. **Проскануйте структуру.** Чи є всі очікувані розділи? Чи є розділ з припущеннями
   (assumptions) та обмеженнями (limitations)?
3. **Перевірте наявність якорів.** Кожне технічне твердження має посилання на джерело
   (рядок коду, тест, коміт). Якщо якорів немає — позначте `needs source anchoring`.
4. **Виконайте всі команди наосліп.** Якщо документ містить команди, а рецензент не запускав
   їх — позначте `commands unverified`. Якщо команди не можна виконати в поточному оточенні —
   це блокуючий finding (порушення *assumptions listed*).
5. **Позначте підозрілі твердження.** Виділіть ті, що виглядають як халюцинації або неточності,
   для другої фази. Якщо таких більше ніж 2-3 на сторінку тексту — поверніть автору на
   доопрацювання без другої фази.

Після першого проходу автор отримує список блокуючих finding-ів.
Якщо блокуючих немає — рецензент переходить до повної перевірки за всіма вісьмома критеріями.

# Investigation brief: плаваюча помилка в refund flow

## Goal

Встановити першопричину розсинхронізації між публікацією події про повернення коштів (refund event) та її споживанням, через яку статус повернення в системі не оновлюється, хоча транзакція в Stripe вже завершена. Результат — обґрунтована гіпотеза з доказами (лог-записи, метрики, діаграма послідовності), без змін коду.

## Scope

- **Область пошуку**: лише модуль `com.example.shop.refunds` та його прямі зв'язки з чергою подій (продюсер + консюмер) і зовнішнім API Stripe. Код поза цим модулем не аналізуємо.
- **Які артефакти досліджуються**: конфігурація черги (топік/черга, retry/dead-letter, acknowledgment mode), логування навколо публікації та обробки події, метрики (latency повідомлень, кількість retry, помилки десеріалізації), обробка винятків у консюмері.
- **Які артефакти НЕ досліджуються**: сам код платіжної інтеграції Stripe (оплата/повернення себто виконання refund), внутрішній білінг, UI/API-шари за межами refund-модуля, тести.
- **Профайл навантаження**: епізодичний — створюємо сценарій із конкуруючими споживачами (concurrent consumers) під помірним навантаженням, аби збільшити ймовірність відтворення.

## Output contract

Документ повернення має містити такі секції:

### summary
- Підсумок знайденого — одне речення з першопричиною.
- Короткий опис механізму збою.
- За яких умов він спрацьовує.

### citations
- Посилання на конкретні фрагменти логів, метрик, рядки в коді (лише readonly — без пропозицій змін).
- Конфігураційні параметри черги (кількість споживачів, retry policy, TTL повідомлень).
- Таймстемпи повторюваного патерну (приклад: помилка припадає на момент масштабування консюмера).

### assumptions
- Які припущення зроблено під час аналізу, що не підтверджені прямим доказом.
- Що прийнято за належне (напр., "Stripe API повертає `succeeded` у 100 % випадків").
- Що лишається поза контролем (напр., поведінка брокера черги під час burst load).

### open questions
- Що неможливо перевірити без зміни коду / інструментування.
- Де бракує логів або метрик.
- Що потребує підтвердження від інфраструктурної команди (конфіг брокера, мережеві політики).

### next steps
- Які експерименти (без зміни коду) можна виконати для підтвердження гіпотези (напр., додати логування на рівні консюмера через тимчасову зміну рівня логу в конфігурації).
- Що слід зафіксувати в метриках / дашборді для спостереження.
- Кому передати естафету (якщо проблема в інфраструктурному шарі).

## Non-goals

- **Не змінювати код** — жодних патчів, рефакторингу або виправлень у межах цього розслідування.
- **Не переписувати платіжну інтеграцію** — будь-які пропозиції щодо зміни механізму роботи з Stripe вважаються виходом за межі.
- **Не оптимізувати продуктивність** — ціль не в тому, щоб "пришвидшити", а в тому, щоб виявити джерело втрати подій.
- **Не покривати сценарії, де гроші не повернуто в Stripe** — підозра стосується лише кейсів, де Stripe успішно повернув кошти, а статус у системі не оновлено.

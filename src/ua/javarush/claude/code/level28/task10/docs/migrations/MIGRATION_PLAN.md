# План міграції cashflow

## Goal

Перенести сервіс `cashflow` з поточного технологічного стеку на цільові версії без зміни спостережуваної поведінки API, автентифікації, бізнес-помилок, health endpoint і формату дат. У межах цього документа описується лише планування; фактичне виконання міграції не входить до scope.

## Scope

- Оновлення Java toolchain з 11 до 17.
- Оновлення Spring Boot з 2.7.18 до 3.2.x.
- Перехід API імпортів і залежностей із `javax.*` на `jakarta.*` там, де це потрібно для цільового стеку.
- Оновлення Spring Security 5.x до 6.x із відтворенням чинної поведінки filter chain.
- Оновлення Flyway з 8.5.13 до 9.x та перевірка застосування наявних міграцій V1..V12.
- Оновлення PostgreSQL driver з 42.5.4 до 42.7.x.
- Збереження Jackson-конфігурації часової зони UTC.
- Порівняння поведінки сервісу до і після кожної контрольної точки.

## Non-goals

- Зміна бізнес-логіки білінгу або правил роботи з підписками.
- Додавання нових API flows, endpoint-ів чи форматів відповідей.
- Перепроєктування схеми PostgreSQL або переписування історії міграцій.
- Зміна кодів бізнес-помилок, політики автентифікації чи статусу health endpoint.
- Оптимізація продуктивності, зміна observability stack або незалежний рефакторинг, не потрібний для сумісності.
- Повний production rollout у межах цієї фази планування.

## Target versions

| Компонент | Поточна версія | Цільова версія |
|---|---:|---:|
| Java | 11 | 17 |
| Spring Boot | 2.7.18 | 3.2.x |
| Spring Security | 5.x | 6.x |
| API-пакети | `javax.*` | `jakarta.*` |
| Flyway | 8.5.13 | 9.x |
| Jackson / часова зона | UTC | UTC |
| PostgreSQL driver | 42.5.4 | 42.7.x |

## Feature-parity contract

Після міграції наведені behaviors мають залишитися незмінними для тих самих вхідних даних і стану сховища:

1. `GET /api/v1/subscriptions/{id}` повертає HTTP 200 і дані підписки, якщо підписка існує.
2. `GET /api/v1/subscriptions/{id}` повертає HTTP 404, якщо підписка відсутня.
3. `GET /api/v1/subscriptions` повертає список підписок із тією самою семантикою та сумісною структурою відповіді.
4. Дати в JSON-відповідях серіалізуються в ISO-8601 у часовій зоні UTC; зміна локальної часової зони середовища не змінює цей контракт.
5. Бізнес-помилки повертаються зі стабільними кодами, зокрема `BILLING_ACCOUNT_SUSPENDED` і `SUBSCRIPTION_NOT_FOUND`.
6. Невалідний або відсутній токен призводить до HTTP 401, а валідний токен зберігає чинну авторизаційну поведінку.
7. Health endpoint повідомляє статус `UP`, коли сервіс і його необхідні залежності доступні.
8. Існуючі дані та міграції V1..V12 залишаються доступними без непередбаченого перетворення або втрати даних.

## Phases

### Baseline

- Зафіксувати версії залежностей, конфігурацію середовища та контрольний стан бази даних.
- Запустити на поточному стеку контрактні перевірки для всіх behaviors з розділу `Feature-parity contract`.
- Зберегти результати відповідей, HTTP-статуси, коди помилок, часові значення в UTC, статус health endpoint і результат застосування V1..V12.

**Gate:** baseline проходить без відхилень від контракту; усі результати та відомі винятки зафіксовані, а для Flyway є відтворюваний спосіб перевірки стану міграцій.

**Rollback point:** поточний реліз на Java 11 / Spring Boot 2.7.18 / Flyway 8.5.13 залишається незмінним і є єдиною версією для відновлення. Якщо baseline неповний, до наступної фази не переходити.

### Pilot

- Застосувати цільовий стек лише до вузького slice: читання однієї існуючої підписки через `GET /api/v1/subscriptions/{id}` у не-production середовищі.
- Перевірити для цього slice успішну відповідь, випадок відсутньої підписки, 401 для відсутнього/невалідного токена, формат дат і стабільність бізнес-коду помилки.
- Окремо виконати перевірку запуску з копією схеми та застосуванням V1..V12; не вважати успішний pilot доказом сумісності всіх flows.

**Gate:** вузький read-only slice відповідає baseline за статусами, payload, кодами помилок і UTC-датами; запуск і перевірка Flyway завершуються без необґрунтованих змін даних; немає blocker-регресій у `jakarta.*` або Security 6.

**Rollback point:** вимкнути pilot і повернути трафік/перевірки на baseline-версію, відкинути лише ізольоване не-production розгортання. Дані production не змінюються pilot-ом.

### Broader update

- Розширити цільовий стек на інші read flows: список підписок, повні сценарії помилок, health endpoint і перевірки автентифікації.
- Прогнати контрактні, інтеграційні та smoke-перевірки на representative dataset.
- Перевірити повторний запуск, порядок і checksum міграцій V1..V12 на копії production-подібної бази.
- Виконувати rollout поетапно, з можливістю залишити baseline як паралельний шлях до завершення gate.

**Gate:** усі flows із контракту мають parity з baseline; немає помилок у логах запуску чи міграцій; health endpoint стабільно `UP`; дані, коди 401/404 і ISO-8601 UTC-представлення збігаються з очікуваннями; операційна команда підтвердила готовність до cleanup.

**Rollback point:** зупинити розширення, повернути маршрутизацію на baseline і відновити попередній runtime. Якщо цільова версія вже торкнулася схеми або даних, rollback виконувати лише за заздалегідь перевіреним backup/restore планом; не запускати зворотні міграції без окремого рішення та evidence.

### Cleanup

- Після стабілізаційного періоду та підтвердження метрик прибрати тимчасову dual-run/маршрутизацію, pilot-конфігурацію і застарілі compatibility toggles.
- Зафіксувати фактичні версії, результати validation і остаточне рішення щодо підтримки baseline.
- Оновити операційні інструкції та залишити rollback-артефакти доступними протягом погодженого retention period.

**Gate:** немає невирішених parity-регресій або blocker-ризиків; цільова версія стабільно обслуговує всі flows протягом погодженого періоду; backup, журнали та інструкція rollback перевірені.

**Rollback point:** до завершення retention period повернутися на збережений baseline через попередню процедуру deployment/restore. Після видалення compatibility-артефактів rollback потребує окремого погодження і може бути не миттєвим.

## Planned validation

1. **Build/toolchain:** зібрати проєкт на Java 17, перевірити тести та відсутність залишкових несумісних `javax.*` імпортів у міграційному scope.
2. **API contract:** для існуючої та відсутньої підписки перевірити `200`/`404`, структуру payload і список підписок.
3. **Authentication:** перевірити відсутній, невалідний і валідний токен; очікуваний результат для перших двох випадків — `401`.
4. **Error contract:** перевірити стабільні коди `BILLING_ACCOUNT_SUSPENDED` і `SUBSCRIPTION_NOT_FOUND` та відповідні HTTP-відповіді.
5. **Serialization:** порівняти JSON із baseline, зокрема ISO-8601 дати в UTC, за різних timezone налаштувань процесу.
6. **Health/smoke:** перевірити, що health endpoint повертає `UP` після старту та після підключення до PostgreSQL.
7. **Persistence:** на копії даних виконати читання та перевірити відсутність втрати/неочікуваної зміни записів.
8. **Flyway:** застосувати V1..V12 на чистій базі, перевірити checksum і повторний запуск на вже мігрованій базі.
9. **Regression comparison:** порівнювати не внутрішню реалізацію, а HTTP-статуси, заголовки, observable payload, коди помилок, health status і дані міграцій.
10. **Operational checks:** перевірити startup logs, readiness, помилки підключення до бази та можливість зупинки rollout за gate.

## Rollback expectation

Rollback має бути можливим на кожній фазі до моменту навмисного видалення baseline-артефактів. Основний шлях — зупинити rollout і розгорнути попередній runtime з незміненим застосунком та відновити маршрутизацію на нього. Перед Broader update потрібні backup/restore rehearsal і перевірений deployment artifact для baseline.

Якщо Flyway 9 уже змінив стан бази або checksum, не виконувати автоматичний downgrade чи ручне редагування історії міграцій. Спочатку зупинити rollout, зафіксувати стан, оцінити сумісність і, за потреби, відновити базу з перевіреного backup. Rollback вважається завершеним лише після повторної перевірки feature-parity contract, health status і читання контрольних даних.

## Open risks

- Spring Security 6 може змінити поведінку filter chain і призвести до неправильних 401 або авторизаційних результатів.
- Перехід `javax.*` → `jakarta.*` може спричинити регресії persistence, валідації або мапінгу.
- Сумісність Flyway 9 із наявними міграціями V1..V12 ще не підтверджена evidence.
- Неправильна конфігурація timezone може змінити UTC-серіалізацію та пошкодити downstream parsing.
- Відмінності між production і pilot-даними можуть приховати проблеми з persistence або міграціями.
- PostgreSQL driver 42.7.x потребує перевірки підключення, транзакцій і edge cases у цільовому середовищі.
- Rollback після зміни схеми не є безумовно безпечним без актуального backup і rehearsal.
- Будь-які зміни бізнес-логіки білінгу поза цим планом можуть зробити порівняння parity недійсним.

# План міграції cashflow

> **Статус:** лише планування. Цей документ не описує виконання міграції, не містить команд запуску та не змінює схему або дані.

## Feature-parity contract

Після переходу на цільовий стек (Java 17, Spring Boot 3.2, `jakarta.*` і Flyway 9) зовнішня поведінка сервісу має залишатися еквівалентною поточній. Функціональна паритетність вважається збереженою лише за одночасного виконання всіх умов:

- `GET /api/v1/subscriptions/{id}` повертає підписку зі статусом 200, а для відсутнього ідентифікатора — статус 404.
- `GET /api/v1/subscriptions` повертає список підписок із тією самою семантикою та структурою відповіді.
- Дати у JSON-відповідях мають формат ISO-8601 і часову зону UTC.
- Бізнес-помилки зберігають стабільні коди, зокрема `BILLING_ACCOUNT_SUSPENDED` і `SUBSCRIPTION_NOT_FOUND`.
- Відсутній, невалідний або неприйнятний токен призводить до статусу 401.
- Health endpoint повідомляє статус `UP` за справного застосунку та його залежностей.
- Поведінка, не перелічена в цьому контракті, не вважається автоматично зміненою: її потрібно окремо зафіксувати як ризик або відкрите питання.

Критерій виходу для кожної наступної фази: жодна перевірена умова контракту не має регресії порівняно з baseline, а невирішені відхилення мають бути явно задокументовані та прийняті відповідальною стороною.

## Обмеження та передумови

- Поточна база порівняння — поведінка, описана в `behavior-inventory.md` і `current-state.md`.
- Цільовий стек і відомі зони сумісності — у `COMPATIBILITY_MATRIX.md`.
- Особлива увага потрібна переходам `javax.persistence` → `jakarta.persistence`, `javax.validation` → `jakarta.validation`, servlet API та Spring Security 6 lambda DSL.
- Сумісність Flyway 9 з наявними міграціями V1–V12 є відкритим питанням і не може вважатися доведеною без evidence.
- На всіх етапах зберігаються UTC, стабільні коди помилок і поточний контракт авторизації.

## Фази та rollback points

### Baseline

**Мета:** зафіксувати відтворюваний опис поточної поведінки до будь-яких змін.

**Очікуваний результат:** погоджений набір baseline-спостережень для API, помилок, авторизації, health endpoint, часових зон і стану міграцій V1–V12. Для кожного спостереження мають бути відомі вхідні умови та очікуваний результат, без внесення змін у систему.

**Gate:** baseline повний для всіх пунктів Feature-parity contract; evidence збережено у вигляді результатів перевірок; відкриті питання, зокрема щодо Flyway, мають власників і критерії розв’язання.

**Rollback point:** `B0 — Baseline accepted`. Будь-яке подальше планове рішення можна відкотити до зафіксованого опису поточного стану без трактування неперевіреної поведінки як нової норми.

### Pilot

**Мета:** оцінити міграційні зміни на обмеженому, ізольованому обсязі та перевірити найбільш ризикові адаптації без зміни загального споживчого контракту.

**Фокус:** компіляційна та інтеграційна сумісність `jakarta.*`, конфігурації Spring Boot 3.2/Security 6, серіалізація UTC, а також читання й валідація історії Flyway V1–V12 у цільовому середовищі.

**Gate:** pilot демонструє еквівалентні відповіді для всіх контрактних сценаріїв; перевірки авторизації, health endpoint і кодів помилок успішні; дані та схеми не зазнали непогоджених змін; сумісність Flyway має позитивне evidence або зафіксований блокер, що зупиняє подальше розширення.

**Rollback point:** `P1 — Pilot isolated`. Результати pilot відкидаються як кандидат на подальше розширення, якщо Gate не пройдений; baseline залишається єдиним прийнятим еталоном, а виявлені відхилення повертаються до черги аналізу.

### Broader update

**Мета:** розширити підтверджений підхід на решту запланованих компонентів, зберігаючи поетапність і можливість повернення до попереднього прийнятого стану.

**Фокус:** повне узгодження залежностей і пакетів, усіх сутностей та валідації, security filter chain, конфігурації Jackson UTC і поведінки бази даних. Розширення допускається лише для частин, що відповідають результатам Pilot.

**Gate:** кожна розширена область має власне evidence; повний Feature-parity contract проходить порівняння з baseline; немає непояснених змін HTTP-статусів, JSON-форматів, кодів помилок, доступу або health-статусу; план повернення для кожної області погоджений до її прийняття.

**Rollback point:** `B1 — Broader update checkpoint`. Останній прийнятий checkpoint є межею повернення для розширеної області. Неприйнята область не блокує відновлення попереднього checkpoint і не стає підставою для визнання міграції завершеною.

### Cleanup

**Мета:** підготувати опис та критерії завершення після підтвердження паритету, не видаляючи артефакти чи сумісні шляхи передчасно.

**Фокус:** підтвердження відсутності залишкових `javax.*`-залежностей у погодженому обсязі, актуалізація документації та матриці сумісності, фіксація прийнятих винятків і завершення відкритих питань. Cleanup не включає видалення даних, історії міграцій або механізмів повернення.

**Gate:** усі контрактні перевірки мають позитивний результат; залишкові відмінності або винятки задокументовані й прийняті; evidence доступне для аудиту; rollback plan залишається зрозумілим після завершення cleanup.

**Rollback point:** `C1 — Cleanup accepted`. Якщо після cleanup виявлено регресію, відновлення орієнтується на останній прийнятий `B1` або інший явно позначений checkpoint, а cleanup-артефакти не вважаються доказом успішності самі по собі.

## Planned validation

Валідація планується як порівняння target candidate з `B0` за однакових вхідних умов і тестових даних. Вона має охопити:

1. Контрактні сценарії обох subscription endpoint: успішне отримання, відсутній ресурс і список.
2. Формат, точність і UTC-часову зону дат у відповідях.
3. Стабільність бізнес-кодів `BILLING_ACCOUNT_SUSPENDED` та `SUBSCRIPTION_NOT_FOUND`.
4. Наявний, відсутній і невалідний токен із очікуваним 401.
5. Health endpoint зі статусом `UP`.
6. Застосування та читання Flyway-історії V1–V12 без непогоджених змін схеми або даних.
7. Перевірку всіх фазових Gate і збереження evidence разом із версією порівнюваного candidate.

Результат кожної перевірки має містити очікуваний результат, фактичний результат, статус, посилання на evidence та рішення щодо подальшого переходу. Валідація не є дозволом на виконання міграції й не замінює окремого погодження релізу.

## Rollback expectation

Rollback очікується як контрольоване повернення до останнього прийнятого checkpoint, а не як виправлення наслідків невідомої зміни. Для кожної фази до проходження Gate мають бути визначені:

- останній прийнятий checkpoint (`B0`, `P1`, `B1` або `C1` залежно від фази);
- ознаки, що вимагають повернення: будь-яка регресія Feature-parity contract, непояснена зміна схеми чи даних, невдале health-поведінка або непідтверджена сумісність Flyway;
- відповідальна сторона за рішення та перевірку результату повернення;
- набір Planned validation, який повторюється після повернення для підтвердження відновлення baseline-поведінки.

Повернення не повинно передбачати втрату даних, переписування історії Flyway або незворотне видалення старих артефактів. Якщо безпечний checkpoint або доказ відновлення відсутні, наступна фаза не відкривається, а стан позначається як блокований до окремого рішення.

## Критерій завершення плану

План вважається готовим до окремого погодження лише тоді, коли всі чотири Gate мають визначені докази проходження, rollback points зафіксовані, а Feature-parity contract і Planned validation залишаються незмінними протягом оцінювання.

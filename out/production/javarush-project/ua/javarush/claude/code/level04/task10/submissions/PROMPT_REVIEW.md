# Prompt Review — Anti-Pattern Findings

## 1. Fix Everything (найкритичніший anti-pattern)

**Де:** `prompt-a.md`, рядок 3  
**Фраза:** *«Полагодь усе в модулі повернень Commerce OS. Повернення глючать, заодно підчисть сервіс, DTO та UI-статуси, щоб було нормально. Зроби як краще.»*

**Проблема:** Prompt не називає жодної конкретної проблеми — «глючать» не є specification. «Зроби як краще» делегує архітектурні рішення моделі без критеріїв прийняття. Такий prompt генерує величезний diff, який неможливо рецензувати, і з високою ймовірністю ламає суміжні модулі.

**Виправлення:**
```markdown
# Задача: обмежена за обсягом
1. Конкретна помилка: після створення return-запиту статус у БД не оновлюється з PENDING на APPROVED.
2. Очікувана поведінка: після виклику `ReturnService.approve(returnId)` поле `status` має стати `APPROVED`.
3. Файли для зміни: `ReturnService.java`, `ReturnController.java`.
4. Що НЕ змінюємо: DTO, UI-статуси, інші методи сервісу.
```

## 2. Відсутність Non-Goals

**Де:** У всіх трьох промптах (`prompt-a.md`, `prompt-b.md`, `prompt-c.md`)

**Проблема:** Жоден prompt не вказує, чого робити НЕ треба. Це призводить до того, що модель «заодно» рефакторить, переписує, чистить — роздуваючи diff і ризикуючи внести регресії в непов'язаний код.

**Виправлення — додати секцію Non-Goals:**
```markdown
## Non-Goals
- Не рефакторити `RefundService` або суміжні класи.
- Не змінювати DTO та JSON-серіалізацію.
- Не чіпати UI-компоненти й статуси на фронтенді.
- Не змінювати логіку для повернень до 100 доларів.
```

---

## 3. Відсутність Verification Plan

**Де:** У всіх трьох промптах, а також у `session-notes.md`, рядок 7  
**Фраза в нотатках:** *«Claude said it works. Перевірку diff і тести не запускали.»*

**Проблема:** Prompt не вимагає верифікації. Модель повідомляє «it works» без запуску тестів, перевірки diff, або вказівки, як оператор чи QA може підтвердити виправлення. Це робить результат неперевіреним і небезпечним для production.

**Виправлення — додати секцію Verification:**
```markdown
## Verification
1. Запустити `./gradlew test --tests RefundServiceTest` — усі тести мають проходити.
2. Виконати curl-запит: `curl -X POST /api/refund/approve?refundId=500` — має повернути 200 OK.
3. Перевірити, що `returnService.approve()` не викидає винятків для high-value refund.
4. Показати git diff — він має торкатися лише зазначених файлів.
```

## 4. Feature Creep / «Заодно»

**Де:** `prompt-a.md` («заодно підчисть сервіс, DTO та UI-статуси»), `prompt-b.md` («заодно трохи відрефактори refund-сервіс»)

**Проблема:** Обидва промпти додають незаплановану роботу через слово «заодно». Це розмиває фокус задачі, збільшує поверхню змін і ускладнює code review. Кожна зміна має бути окремою задачею.

**Виправлення:**
```markdown
- Прибрати слово «заодно» з формулювання.
- Якщо рефакторинг потрібен — створити окрему задачу з власними Acceptance Criteria.
- Якщо зміна DTO чи UI справді потрібна — додати окремий prompt з обґрунтуванням.
```

## 5. Відсутність Acceptance Criteria

**Де:** Усі три промпти

**Проблема:** Prompt містить лише загальний опис бажаної поведінки, але не визначає, як саме має виглядати успішне виконання. Тільки `prompt-c.md` згадує конкретний конфіг (`refund.autoApprovalThreshold`), але не каже, що саме має статися при перевищенні порогу.

**Виправлення — додати Acceptance Criteria:**
```markdown
## Acceptance Criteria
- [ ] Refund > $100 потребує ручного підтвердження оператора.
- [ ] Refund ≤ $100 проходить автообробку (без змін у поточній логіці).
- [ ] Поріг зчитується з `refund.autoApprovalThreshold` (не хардкод).
- [ ] Якщо конфіг відсутній — використовується значення за замовчуванням $100.
- [ ] Усі існуючі тести проходять без змін.
```

## 6. Polluted Session (ризик)

**Де:** `session-notes.md`, рядки 3–8

**Опис:** Згідно з нотатками, сесія триває довго, модель «все ще посилається на стару гіпотезу про хардкод», «diff стає лише ширшим», а «сесію не очищали». Це класичний **polluted session** — контекстне вікно містить застарілі, суперечливі або нерелевантні обговорення, які впливають на подальші відповіді моделі.

**Як виправити:**
1. Завершити поточну сесію та почати нову з чистим контекстом.
2. У новій сесії надати prompt-c (найкращий з трьох) із доповненням Acceptance Criteria та Non-Goals.
3. Не продовжувати роботу в тій самій сесії після зміни вимог — це джерело hallucinations.

---

## Найнебезпечніший prompt: **prompt-a.md**

**Чому:** `prompt-a.md` («Полагодь усе…») містить одразу три критичні anti-patterns:
1. **Fix Everything** — найгірша форма відкритого завдання, модель сама вирішує, що «глючить» і що «нормально».
2. **Відсутність Non-Goals** — не сказано, які частини системи не чіпати.
3. **Відсутність Verification Plan** — немає способу підтвердити, що щось справді виправлено.

У комбінації з **polluted session** (session-notes показують, що сесія вже брудна) цей prompt майже гарантовано призведе до:
- Величезного diff, що торкається 5+ модулів;
- Непрошеного рефакторингу;
- Регресій у непов'язаних сценаріях;
- Hallucinations про те, якою має бути «правильна» архітектура.

**Рекомендація:** цей prompt не можна відправляти моделі в поточному вигляді. Переписати за шаблоном: конкретна проблема → очікувана поведінка → файли для зміни → non-goals → verification.
